# ミスドリTERM 仕様書

1999年ナムコ「ミスタードリラー」(初代、PlayStation版)っぽい、ターミナル(TUI)で動く縦穴掘りアクションゲームの仕様書。
実装言語はRust。描画はratatui+crossterm、サウンドはrodioを使った自作波形合成音源(実機音源は使用しない)。

## 本書の情報源について

1〜9章は、初代(1999年PS1版)の公式マニュアルと複数の攻略wikiの横断調査で裏付けた事実(以下「確定事実」)に基づく。

本書では以下の2種類の記述を区別する。

- **確定事実**: 公式マニュアル・攻略wiki等の一次情報で裏付けが取れた、初代のルールそのもの
- **TERM独自の設計判断**: 確定事実からは直接導けないが、ターミナル実装として成立させるために本プロジェクトが独自に定めた仕様(例: ダイヤブロック、X/Zキーでの静止掘削、ライフ復帰時の無敵時間など)

TERM独自の設計判断には、その都度その旨を明記する。

## 1. 基本ルール

- プレイヤー(ホリ・ススム)は幅12マスの縦穴を、選択したコースのゴール深度まで掘り進む
- コースは2種類(確定事実): **500m(イージー)** と **1000m(ノーマル)**。タイトルでEnterを押した直後のモードセレクト画面(TERM独自拡張)でどちらかを選び、選んだコースのゴール深度でゲームが始まる
- フィールド幅12マスは初代の実寸に合わせたものではなく、ターミナル表示に収めるためのTERM独自の設計判断
- 1m = 1マス。フィールドは下方向にスクロールする
- 酸素が尽きる、または落下してくるブロックに押し潰されると1ライフを失う。ライフを使い切るとゲームオーバー(8章)
- 選択したコースのゴール深度へ到達するとゲームクリア

### 操作一覧

初代の操作は「移動はD-pad(方向キー)、掘削は専用の1ボタン」という**別入力**である(公式マニュアル: "one button is your drill, while the D-pad or analog stick is your movement")。方向キーの中でも役割が分かれている。

- UP: ドリルを上に向けるだけ(移動しない)
- DOWN: ドリルを下に向けるだけ(移動しない)
- LEFT: 左に移動しつつドリルを左に向ける
- RIGHT: 右に移動しつつドリルを右に向ける
- 専用のドリルボタン: 現在ドリルが向いている方向(facing)を掘削する

**TERM独自の設計判断(重要)**: 上記確定事実のLEFT/RIGHTは「移動しつつ前方を掘削する」挙動だが、TERMではこれをさらに一歩進め、**カーソルキー(←/→/↑/↓)は掘削を一切行わない**設計にする。方向キー入力の一部にだけ暗黙の掘削が混ざっていると、単に移動・向き変更のつもりで押したキーで意図せずブロックを破壊する事故につながるためである。掘削は常に専用のDrillキー(X/Z)を押したときにのみ発生する、という一貫したルールに統一する。

| キー | InputAction | 効果 |
|---|---|---|
| ← | `MoveLeft` | facingをLeftにし、**掘削を伴わない**地形追従の移動を試みる(詳細は下記) |
| → | `MoveRight` | facingをRightにし、**掘削を伴わない**地形追従の移動を試みる(左右対称。詳細は下記) |
| ↑ | `FaceUp` | facingをUpに変更するのみ。移動・掘削は一切発生しない |
| ↓ | `FaceDown` | facingをDownに変更するのみ。移動・掘削は一切発生しない |
| X / Z | `Drill` | 現在のfacing方向のセルを掘削する(下記参照)。どちらのキーでも同じ(TERM独自拡張) |
| Space / P | `TogglePause` | 一時停止/再開(TERM独自拡張。どちらのキーでも有効) |
| Backspace / U | `Rewind` | フレーム巻き戻しを開始する(16章。TERM独自拡張。どちらのキーでも有効) |
| Esc | `Quit` | タイトル画面へ戻る(下記参照。TERM独自拡張) |
| S | `ToggleSound` | サウンド(SE+BGM)のON/OFF切り替え(TERM独自拡張、10章)。タイトル画面・一時停止画面でのみ意味を持つ。プレイ中(Playing)の入力は無視する |

プレイヤーは現在向いている方向を表す `facing: Direction` を状態として保持する(初期値 `Direction::Down`)。

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Direction {
    Up,
    Down,
    Left,
    Right,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum InputAction {
    MoveLeft,
    MoveRight,
    FaceUp,
    FaceDown,
    Drill,
    TogglePause,
    Quit,
    ToggleSound,
}
```

#### ← / → (MoveLeft / MoveRight) の詳細(TERM独自: 掘削なしの地形追従移動)

facingをその方向へ変更したうえで、隣接する1マス先のセルの状態に応じて以下のいずれか1つだけを行う。**掘削は一切発生しない**(色ブロック・岩ブロック・ダイヤブロックについては、Left/Rightの入力では破壊も取得もされない。ただの障害物として扱う)。

**例外(TERM独自の設計判断)**: 隣接する同じ高さのマスが**酸素カプセル**の場合のみ、掘削を伴わずにそのマスへ移動しつつ自動的に取得する。酸素カプセルはEmptyと同様「移動できるマス」として扱われるが、通過した瞬間に酸素+50・スコア加算(既存のカプセル取得処理と同一)が発生する点だけがEmptyと異なる。これにより、掘削(X/Z)を挟まなくても隣を歩くだけでカプセルを回収できる。色ブロック・岩ブロック・ダイヤブロックは従来通り取得にX/Z(Drill)が必須のまま変わらない。

隣接する同じ高さのマスがEmpty、または酸素カプセルの場合は、1段上のマスの状態に関わらず、そのマスへ1マス移動する(酸素カプセルの場合は移動と同時に取得する。これまで通り、1回の入力で完結する)。

隣接する同じ高さのマスが塞がっている(Empty・酸素カプセル以外)場合、**段差登りは1回の入力では完結せず2ステップになる**(TERM独自の設計判断)。隣が塞がっていて1段上が空いているだけで即座に登ってしまうと、ただ隣へ移動したかっただけの入力で意図せず段差を登る事故につながるためである。プレイヤーは直前に「同じ方向へぶつかって停止していたか」を`bumped_direction: Option<Direction>`として保持する。

| 直前に同じ方向へぶつかっていたか | 1段上(row-1)のマス | 処理 |
|---|---|---|
| いいえ(1回目の入力) | (不問) | 登らず、その場に留まる。facingの変更だけが反映され、「この方向にぶつかって停止した」ことを`bumped_direction`に記憶する |
| はい(直前と同じ方向への2回目以降の入力) | Empty、酸素カプセル、またはアイテムブロック | 1段登って斜め上のマスへ移動する(段差を乗り越える)。酸素カプセル・アイテムブロックの場合は登りながら取得する。`bumped_direction`はリセットされる |
| はい(直前と同じ方向への2回目以降の入力) | 上記以外で塞がっている | 登れないため、その場に留まる(1回目と同じ扱い) |

登り判定は登り先(1段上・隣の列)だけでなく、**自分の真上(row-1・同じ列)も見る**(TERM独自の設計判断)。真上が物理ブロック(色ブロック・岩ブロック・ダイヤブロック・スターブロック)で塞がっている場合は、登り先が空いていても登れず、その場に留まる(頭上が塞がった状態で斜めに登り抜けるのは不自然なため)。真上が酸素カプセル・アイテムブロックの場合は「触れるだけで取得できる」通過可能なマスとして扱い、通り抜けながら取得して登る(#244)。取得は実際にそのマスへ踏み込んだ時のみ発生するため、真上が通過可能でも登り先が塞がって登れなかった場合は、真上の酸素カプセル・アイテムブロックもそのまま残る。真上と登り先の両方に酸素カプセル・アイテムブロックがある場合は2マス分まとめて取得する。

方向を変えずに同じ方向へ2回連続で入力しないと登れない。別の方向キー(逆方向のLeft/Right、またはUp/Down)を挟んだり、Drill(X/Z)キーを挟んだりすると`bumped_direction`はリセットされ、また1回目からやり直しになる。いずれの場合も、ブロックは一切破壊されずそのまま残る。

フィールド端(列0の左、列11の右)へ向けた入力は何も起きない(facingの変更も含め完全なno-op)。最上段(row=0)では「1段上」が存在しないため、隣接マスが塞がっていれば(2回目の入力であっても)無条件でその場に留まる。

#### X/Z(Drill)の詳細

facing方向にある1マス先のセルを、**移動を伴わずに**掘削する。

| facing | 効果 |
|---|---|
| Down | 直下のセルを掘削する。掘削(または既にEmpty)の結果そのマスが空いていれば、続けて1マス下降する。岩ブロックが5回未満のヒットで破壊に至らなかった場合は下降しない |
| Up | 掘削を試みるが、初代準拠で「登った穴を掘り直す」概念自体が存在しないため実質的な効果は無い(入力自体は受理してよい) |
| Left / Right | その場から動かず、その方向のセルを掘削する(色ブロックなら連結消滅、岩ブロックならヒット蓄積/破壊、酸素カプセル/ダイヤなら取得)。**移動はしない** |

Left/Right方向へのDrillは、その場に留まったまま前方の岩ブロックへヒットを蓄積したい場合や、隣接する酸素カプセル/ダイヤを取得したい場合に使う、TERM独自の設計判断による操作である。カーソルキーは掘削を行わないため、**色ブロック・岩ブロック・酸素カプセル・ダイヤブロックを取得/破壊する手段はX/Z(Drill)キーのみ**になる。

#### プレイヤー自身の自由落下(TERM独自拡張)

色ブロック等と同じ`FALL_TICK_MS`(13章)ごとの論理ティックで、入力の有無や掘削操作とは無関係に、プレイヤーの直下のマスを毎回判定する。直下がフィールド内かつEmptyであれば、そのティックでプレイヤーは1マス落下する。支え(直下が非Emptyなセル、または既に最深行にいる)がある限り、これは発生しない。掘削で足元の支えを失った場合や、1段登った先の足元がたまたま空洞だった場合など、プレイヤー自身にも他のブロックと同様の重力が働く(4章参照。ただし色ブロックのような`SHAKE_TICKS`ぶんの「揺れ」の猶予は無く、支えを失った次のティックで即座に落下する)。

#### Esc(Quit)の詳細: タイトル画面への遷移

Escキーは常に「タイトル画面へ戻る」動作であり、押されたのがどの画面かによって結果が変わる(TERM独自の設計判断)。

| 押された画面 | 結果 |
|---|---|
| タイトル画面 | アプリケーションを終了する |
| プレイ中/一時停止中/ゲームオーバー画面/クリア画面 | タイトル画面へ戻る。進行中のゲーム状態(酸素・スコア・深度・ライフ・盤面)は全て破棄され、次にゲームを開始する際は新しい乱数シードで盤面を生成し直す |

タイトル画面は、ゲーム名の表示と「何かキーを押してスタート」程度のシンプルな画面でよい。タイトル画面上でEsc(終了)・S(設定画面)・H(ヘルプ画面)以外の任意のキーを押すと、新しいゲームを開始してプレイ中画面へ遷移する。

## 2. フィールドとブロック

### フィールド構造

- 幅: 12マス(列インデックス0〜11。初代の実寸ではなくTERM独自の表示上の設計値)
- 深さ: コースにより500マスまたは1000マス(行インデックス0始まり、行インデックス=深度[m]-1)
- データ構造は `Vec<[Cell; 12]>` (要素数はコース長)を想定。1行=1m分の横一列

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Cell {
    Empty,
    Color(ColorKind),
    /// 岩ブロック(Xブロック)。破壊されるまでの累積ヒット数(0〜4)を保持する。
    /// 5回目のヒットで破壊される(確定事実: "require five strikes before they break")。
    Rock { hits: u8 },
    Oxygen,
    /// ダイヤブロック。TERM独自拡張(初代の確定事実には存在しない要素。11項参照)。
    Diamond,
}

/// 通常ブロックの色。初代は4色(赤・青・緑・黄)。紫は存在しない。
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum ColorKind {
    Red,
    Blue,
    Green,
    Yellow,
}

impl ColorKind {
    pub const ALL: [ColorKind; 4] = [
        ColorKind::Red,
        ColorKind::Blue,
        ColorKind::Green,
        ColorKind::Yellow,
    ];
}
```

掘削可否・得点・連結消滅の詳細ルールは4章・7章で定める。

### ブロック種類

| 種類 | 見た目 | 取得/掘削 | 効果 |
|---|---|---|---|
| 色ブロック(赤/青/緑/黄、4色) | 樽型の色付きブロック(9章) | 掘削可(1ヒットで破壊) | 4方向に連結している同色グループごと即座に消滅する(4章)。消滅した1ブロックにつき10点(7章) |
| 岩ブロック(Xブロック) | 茶色の樽型ブロック、表面にXマーク | 掘削可(累積5ヒットで破壊) | 破壊時に酸素-20%(連結して巻き込まれた分を含め1回のみ)。得点は無し。岩ブロック同士は4方向連結・自動消滅の対象になる(TERM独自の設計判断、4.9章) |
| 酸素カプセル(Air Capsule) | 水色の専用グリフ | 掘削でも取得可。**隣接マスへの移動(1章MoveLeft/MoveRight)だけでも自動的に取得できる**(TERM独自の設計判断、掘削不要) | 酸素+50(上限100でクランプ)。n個目の取得でn×100点(7章) |
| ダイヤブロック(TERM独自拡張) | 白/水色の専用グリフ | 掘削可(1ヒットで破壊)。移動だけでは取得できない | 得点+500(即時加算)。初代の確定事実には存在しない要素(11項参照) |

- 岩ブロックは色ブロックと同様に4方向連結・落下後の自動消滅の対象になる(TERM独自の設計判断。詳細は4.9章)。ただし得点は発生せず、掘削による5回ヒット耐久ルールも維持する
- 酸素カプセル・ダイヤブロックは常に連結グループの対象外(4章の「4方向連結」判定に一切参加しない)
- ただし岩ブロック・酸素カプセル・ダイヤブロックも**重力の対象にはなる**(支えを失えば他の色ブロックと同様に落下する。4章)。連結グループの対象外というのは「同色でまとまって消える」ロジックの対象外という意味であり、「落下しない」という意味ではない

### 開始地点の安全確保

- 深度0〜1m(先頭2行)はブロック生成テーブルを適用せず、全マスEmpty固定とする
- これにより開始直後に落下ブロックへ巻き込まれる事故を防ぐ

## 3. ブロック生成アルゴリズム

マスごとに完全独立した乱数でセルの中身を決めると、同色が固まらずランダムなドット絵のような見た目になってしまう。そのため生成を2段階に分離する。

1. **色ブロックの下地生成(3.2〜3.4)**: 岩・酸素・ダイヤのことは一旦考えず、全マスに必ず4色いずれかの色を割り当てる。隣接セルの色に引きずられる近傍依存の抽選を行い、同色が面としてまとまりやすくする
2. **岩・酸素・ダイヤの上書き配置(3.5)**: 1で作った色の下地の上から、深度帯別テーブル(3.1)の確率でマスごとに独立抽選し、当たったマスだけ岩/酸素/ダイヤへ上書きする(外れたマスは1で決めた色のまま残る)

この2段階に分けることで、「同色の塊を作る」という視覚的な要求と、「深度が増すごとに岩・酸素・ダイヤの出現率が変わる」というゲームバランスを両立させる。

(TERM独自の設計判断: この2段階生成アルゴリズムそのものは確定事実に基づくものではなく、初代のプレイ画面で色ブロックが面としてまとまって見える見た目に近づけるためのTERM独自の実装である)

### 3.1 深度帯別 出現確率テーブル(岩・酸素・ダイヤ)

| 深度帯 | 岩 | 酸素カプセル | ダイヤブロック | 残り(色ブロック合計・4色均等) |
|---|---|---|---|---|
| 0〜199m | 5% | 3% | 2% | 90%(各色22.5%) |
| 200〜399m | 8% | 4% | 3% | 85%(各色21.25%) |
| 400〜599m | 12% | 4% | 4% | 80%(各色20%) |
| 600〜799m | 16% | 4% | 5% | 75%(各色18.75%) |
| 800〜999m | 20% | 4% | 6% | 70%(各色17.5%) |

各行の合計は必ず100%になる。500mコースの場合はこのテーブルのうち0〜499m分のみを使用する。「残り(色ブロック)」列は3.2〜3.4の近傍依存生成では直接参照しない(常に4色均等前提のため、そちらは深度に依存しない)。3.5の上書き判定を経た結果として、最終的な色ブロックの出現率がこの列と一致する(3.5末尾で説明)。

```rust
pub struct BandTable {
    pub rock: f32,
    pub oxygen: f32,
    pub diamond: f32,
    // color_total = 1.0 - rock - oxygen - diamond (常に4色均等なので個別の値は持たない)
}

pub fn band_table(depth_m: u32) -> BandTable {
    match depth_m {
        0..=199   => BandTable { rock: 0.05, oxygen: 0.03, diamond: 0.02 },
        200..=399 => BandTable { rock: 0.08, oxygen: 0.04, diamond: 0.03 },
        400..=599 => BandTable { rock: 0.12, oxygen: 0.04, diamond: 0.04 },
        600..=799 => BandTable { rock: 0.16, oxygen: 0.04, diamond: 0.05 },
        _         => BandTable { rock: 0.20, oxygen: 0.04, diamond: 0.06 },
    }
}
```

### 3.2 色ブロックの下地生成(近傍依存)

各マス`(row, col)`の色は、以下の優先順位で決定する。生成は行を上から下、列を左から右へ**逐次**進めることが前提であり、左隣・上隣のセルは常にこのマスより先に色が確定している(マス単位の並列生成はできないが、コース最大1000行×12列=12,000マス程度の事前生成コストは無視できる)。

1. 乱数`r ∈ [0.0, 1.0)`を1回引く
2. `r < 0.65` かつ 左隣`(row, col-1)`が存在し色ブロックである → 左隣と同色にする
3. 上記に該当せず、`r < 0.90` かつ 上隣`(row-1, col)`が存在し色ブロックである → 上隣と同色にする
4. 上記いずれにも該当しない(左端列で左隣が無い/先頭行で上隣が無い/確率的に完全ランダム側に落ちた) → 4色から均等(各25%)でランダムに1色選ぶ。3.1のテーブルにおける「色ブロック合計」の内訳は深度帯によらず常に4色均等なため、このランダム抽選も深度に関わらず一律25%ずつでよい

左隣0.65・上隣0.90という閾値はTERM独自の調整値である。統計検証(横方向の同色ランの平均長が約2.2〜2.3マス)で、横方向のまとまりが十分に出ることを確認済み。完全ランダム抽選に落ちる比率は10%になる。

```rust
fn pick_base_color(
    rng: &mut impl RngCore,
    left: Option<ColorKind>,
    top: Option<ColorKind>,
) -> ColorKind {
    let r: f32 = rng.gen_range(0.0..1.0);
    if r < 0.65 {
        if let Some(c) = left {
            return c;
        }
    }
    if r < 0.90 {
        if let Some(c) = top {
            return c;
        }
    }
    ColorKind::ALL[rng.gen_range(0..4)]
}
```

深度0〜1m(先頭2行)は2章の安全地帯規定により全マスEmpty固定のままとし、この生成パス自体を適用しない(生成対象は深度2m行目以降)。

### 3.3 同色連続の上限(横4・縦3)

3.2で決めた色候補が、その時点で確定済みの同色連続本数を超えてしまう場合は、候補色を強制的に別の色へ差し替える。

- **横方向**: 候補マス`(row, col)`について、`(row, col-1)`・`(row, col-2)`・`(row, col-3)`の3マスが全て候補色と同色ならば、そのまま採用すると横5連続になってしまうため差し替える(横方向の同色連続は最大4マスまで)
- **縦方向**: 候補マス`(row, col)`について、`(row-1, col)`・`(row-2, col)`の2マスが全て候補色と同色ならば、そのまま採用すると縦4連続になってしまうため差し替える(縦方向の同色連続は最大3マスまで)
- 差し替え先の色は追加の乱数を消費せず、`ColorKind::ALL`を固定順(Red, Blue, Green, Yellow)で走査し、横方向・縦方向どちらの制約にも抵触しない最初の色を採用する(4色のうち制約に抵触しうるのは横・縦それぞれ最大1色なので、必ず2色以上が候補として残る)

```rust
fn resolve_run_limits(
    candidate: ColorKind,
    left3: [Option<ColorKind>; 3], // (row,col-1),(row,col-2),(row,col-3)
    top2: [Option<ColorKind>; 2],  // (row-1,col),(row-2,col)
) -> ColorKind {
    let breaks_horizontal = |c: ColorKind| left3.iter().all(|n| *n == Some(c));
    let breaks_vertical = |c: ColorKind| top2.iter().all(|n| *n == Some(c));

    if !breaks_horizontal(candidate) && !breaks_vertical(candidate) {
        return candidate;
    }
    ColorKind::ALL
        .into_iter()
        .find(|&c| !breaks_horizontal(c) && !breaks_vertical(c))
        .expect("4色中2色以上は必ず両条件を満たす")
}
```

### 3.4 孤立セルの解消(生成後の後処理)

3.2〜3.3でコース全行の色下地を生成し終えた後、盤面全体に対して1回だけ以下の後処理を行う。

- マス`(row, col)`が「孤立している」とは、上下左右4方向の隣接マスのうち、盤面内に存在し**かつ同色の色ブロックであるものが1つも無い**ことをいう(隣接マスがEmpty/盤外/別の色ならカウントしない)
- 孤立しているマスは、存在する隣接色ブロックの色を集計し、最も出現数が多い色に置換する。同数で並んだ場合は`ColorKind::ALL`の順(Red, Blue, Green, Yellow)で先に来る色を採用する
- 隣接マスに色ブロックが1つも無い(四方全てEmpty/盤外)場合は置換しない(そのまま孤立させておく。極めて稀なケースであり実害が小さいため)
- この後処理は3.3の連続数上限を再チェックしない。置換の結果、ごく稀に横5連続・縦4連続が新たに発生する可能性を許容する(「浮いた1マスを無くして塊を作る」ことを優先するトレードオフとして明記しておく)

```rust
fn fix_isolated_cells(base: &mut [[ColorKind; FIELD_WIDTH]]) {
    let rows = base.len();
    for row in 0..rows {
        for col in 0..FIELD_WIDTH {
            let me = base[row][col];
            let neighbors = same_color_neighbors_candidates(base, row, col); // 上下左右のうち盤内のものの色一覧
            let is_isolated = !neighbors.iter().any(|&c| c == me);
            if is_isolated && !neighbors.is_empty() {
                base[row][col] = most_common_color(&neighbors); // 同数はColorKind::ALL順で先勝ち
            }
        }
    }
}
```

### 3.5 岩・酸素・ダイヤの上書き配置

3.2〜3.4で確定した「色ブロックのみの下地盤面」に対し、深度帯別テーブル(3.1)の確率でマスごとに独立抽選を行い、上書きする。この段階は近傍依存にしない(岩・酸素・ダイヤは4章の通り常に単独扱いで同色の塊を作る対象ではないため、隣接関係を考慮する必要が無い)。

```rust
pub fn overlay_rock_oxygen_diamond(
    rng: &mut impl RngCore,
    base_color: ColorKind,
    depth_m: u32,
) -> Cell {
    let t = band_table(depth_m);
    let r: f32 = rng.gen_range(0.0..1.0);
    if r < t.rock {
        Cell::Rock { hits: 0 }
    } else if r < t.rock + t.oxygen {
        Cell::Oxygen
    } else if r < t.rock + t.oxygen + t.diamond {
        Cell::Diamond
    } else {
        Cell::Color(base_color)
    }
}
```

この式により、最終的な岩・酸素・ダイヤの出現率は3.1のテーブル値と厳密に一致する(下地の色が何であっても上書き確率自体は変わらないため)。同様に、上書きされなかったマスの割合`1 - rock - oxygen - diamond`が3.1の「残り(色ブロック合計)」列と一致する。

### 3.6 生成手順まとめ(擬似コード)

```rust
pub fn generate_row(
    rng: &mut impl RngCore,
    depth_m: u32,
    prev_row_base: Option<&[ColorKind; FIELD_WIDTH]>, // 直前行の色下地(3.2〜3.3反映済み)
) -> ([ColorKind; FIELD_WIDTH], [Cell; FIELD_WIDTH]) {
    if depth_m < 2 {
        return ([ColorKind::Red; FIELD_WIDTH], [Cell::Empty; FIELD_WIDTH]);
    }

    let mut base = [ColorKind::Red; FIELD_WIDTH];
    for col in 0..FIELD_WIDTH {
        let left = if col == 0 { None } else { Some(base[col - 1]) };
        let top = prev_row_base.map(|r| r[col]);
        let candidate = pick_base_color(rng, left, top);
        base[col] = resolve_run_limits(candidate, left3_of(&base, col), top2_of(prev_row_base, col));
    }
    // 全行生成後、盤面全体に対し fix_isolated_cells (3.4) を1回だけ実行する(行単位のこの関数の外側で行う)。

    let mut cells = [Cell::Empty; FIELD_WIDTH];
    for col in 0..FIELD_WIDTH {
        cells[col] = overlay_rock_oxygen_diamond(rng, base[col], depth_m);
    }
    (base, cells)
}
```

- 盤面全体(コース長=500行または1000行)は起動時に1回、乱数シード(u64)から事前生成する(通常プレイはOS乱数から生成したシード、タイムアタック/対戦は固定・共有シードを使用。詳細は11章・12章)
- 乱数生成器は`rand_chacha::ChaCha8Rng`(シード指定可能・決定的)を使用する。3.2の下地生成→3.3の連続数抑制を全行分行い、その後3.4の孤立セル解消を盤面全体に1回、最後に3.5の上書きを全マスに適用する。この順序を守り、生成し直しは行わない

## 4. 落下・連結・消滅ロジック

初代の確定事実は次の3点である。

1. 「Blocks of the same color form groups which disappear when Mr. Driller breaks any one of them」— 同色ブロックが4方向連結してグループを形成しているとき、そのどれか1つを掘削で破壊すると、連結しているグループ全体が即座に消滅する
2. 「Unsupported blocks fall. Falling blocks will stop falling when they meet another supported block of the same color.」— 支えを失ったブロックは1マスずつ落下する。落下中のブロックは、支えられている同色ブロックに接触すると停止し、そこに連結する
3. 「Falling blocks that meet and connect to the same color blocks to make four or more will disappear without being drilled.」— 連結の結果グループが4個以上になった場合、掘削されなくても自動的に消滅する。3個以下ならそのまま留まり、新しい支えとして固定される

以下、これらを実装可能な粒度まで具体化する。

### 4.1 対象

- **重力(支えを失うと落下する)の対象**: 色ブロック・岩ブロック・酸素カプセル・ダイヤブロックの全て
- **プレイヤー自身の自由落下(TERM独自拡張、1章参照)**: プレイヤーも上記ブロック群と同様に、直下がEmptyなら支えを失った扱いで落下する。ただしブロックの重力とは別の判定として実装する。直下がEmptyかどうかを毎ティック単純に見るだけで、4.3の`SHAKE_TICKS`ぶんの「揺れ」の猶予は無く、支えを失った次のティックで即座に1マス落ちる。プレイヤーの落下自体が5章の押し潰し判定を発火させることはない(押し潰しは常に「ブロックがプレイヤーの位置へ落ちてくる」側の判定であり、両者は独立した仕組みである)
- **4方向連結によるグループ形成・自動消滅の対象**: 色ブロック(同色同士)・**岩ブロック(hits値に関わらず岩ブロック同士。TERM独自の設計判断、4.9参照)**。酸素カプセル・ダイヤブロックはこのロジックに一切参加しない(常に単独として振る舞う)
  - 確定事実1〜3(本章冒頭)が原文で述べているのは色ブロックについてのみだが、TERM独自の設計判断として岩ブロックにも同じ4方向連結ルール(未支持→揺れ→落下→連結→4個以上で自動消滅)を適用する。掘削による5回ヒットでの耐久ルール(2章)自体は変更しない(4.9参照)

### 4.2 支持判定(Support)

あるセル`(row, col)`が「支持されている」とは、以下のいずれかを満たすことをいう。

- `row`がコース最深行であり、直下の行が存在しない
- 直下のセル`(row+1, col)`が空(Empty)でない、かつプレイヤーが`(row+1, col)`にいない

**プレイヤーの現在位置は常に「空洞」として扱う**(プレイヤーが支えの代わりになることはない。5章の押し潰し判定と対になる仕様)。

支持されていないセルは「未支持」であり、落下対象になる。

### 4.3 揺れ(Shake)演出

あるセルが直前のティックまで支持されていたのに、今回のティックで未支持になった場合、即座には落下を開始しない。まず`SHAKE_DURATION_MS`(13章、`SHAKE_TICKS`ぶんのティック数に換算)だけ「揺れ」状態で待機し、その後に落下を開始する。これは初代の「掘削されると周囲のブロックが震えてから落ちる」という視覚演出に対応する(9章で描画方法を扱う)。揺れ状態のセルは5章の押し潰し判定の対象にならない(実際に落下し始めてから判定する)。

- `SHAKE_DURATION_MS`は300〜500msの目安幅から、「震えてから落ちる」感覚がわかる450ms(=`FALL_TICK_MS`3ティック分)を採用した(TERM独自の調整値)
- 揺れティック数への換算は、設定値そのものではなく深度補正後の実効ティック間隔で毎回行う。整数除算のため、ティック間隔が揺れ時間を超えると0ティック(揺れ無しでいきなり落ちる)になってしまうので、揺れ時間が0より大きい限り最低1ティックは揺れるものとする(TERM独自拡張)
- 揺れ中かどうかの状態は、重力落下ロジックを保持する`GravityState`(未支持ティック数を内部に持つ)に集約する。この状態自体は副作用のない物理演算とは独立して保持し、`is_shaking(pos)`のようなアクセサ経由で外部から参照できるようにしておく。これにより、次フェーズ以降の描画層がシェイク演出(セルを左右に微振動させる等)を実装する際、追加のデータ構造を持たずにこの状態をそのまま使える(今回のイテレーションでは実際の視覚演出自体はスコープ外。9.11参照)
- 揺れ時間は設定画面の項目『落下待ち時間(揺れ)』から0〜2000msを50ms刻みで調整でき(`,`/`.`キーと同じ値を共有する)、`settings.json`の`shake_duration_ms`に永続化する。0は揺れ無しで即落下する(この場合、頭上の揺れを監視して発動するヒヤリ回避スライダー演出は発火しなくなる)。表示はms単位だが、実際の待ちは内部で実効tick単位に量子化されるため、0より大きい値を設定すれば必ず最低1tickぶんは揺れる

### 4.4 重力ティック処理(スナップショット同時評価)

固定間隔の論理ティック(`FALL_TICK_MS` = 150ms、13章参照)ごとに、以下の手順で全セルを再評価する。

1. ティック開始時点のフィールド全体をスナップショットとして複製する(以後の判定は全てこのスナップショットを基準に行う)
2. スナップショットを基準に、揺れ状態が明けている(かつEmptyでない)全セルについて4.2の支持判定を行い、未支持のセルを列挙する
3. 未支持セルは全て「1マス下へ移動する」対象として確定する。この確定は**スナップショット基準で同時に行う**ため、処理順序に依存しない。例えば3段重なったブロックの下に1マスの隙間がある場合、最下段のブロックだけがそのティックで1マス落ち、中段・上段は次のティック以降に順に落ちていく(=一度に3マスまとめて落ちることはない)
4. 確定した移動を実際のフィールドへ反映する(元の位置をEmptyにし、移動先へ元の内容をコピーする。岩ブロックは`hits`を保持したまま移動する)
5. 移動先がプレイヤーの現在位置と一致するセルがあれば、5章の押し潰し判定を発火させる
6. 移動して着地した(=このティックで新たに動きが止まった)色ブロックについて、4.5の連結・自動消滅判定を行う

```rust
pub fn physics_tick(board: &mut Board, player_pos: (usize, usize)) -> Vec<((usize, usize), (usize, usize))> {
    let snapshot = board.clone();
    let mut moved = Vec::new();

    for row in 0..board.depth_rows() {
        for col in 0..FIELD_WIDTH {
            let pos = (row, col);
            if snapshot.get(pos) == Cell::Empty || board.is_shaking(pos) {
                continue;
            }
            let below = (row + 1, col);
            let supported = row + 1 >= board.depth_rows()
                || (snapshot.get(below) != Cell::Empty && below != player_pos);
            if !supported {
                moved.push((pos, below));
            }
        }
    }

    for &(from, to) in &moved {
        let cell = snapshot.get(from);
        board.set(from, Cell::Empty);
        board.set(to, cell);
    }

    moved // 呼び出し側が押し潰し判定(5章)・連結判定(4.5)に使う
}
```

### 4.5 着地時の連結・自動消滅判定(3.の確定事実。岩ブロックへはTERM独自拡張で適用)

4.4の手順6で「新たに着地した色ブロック・岩ブロック」が生じるたびに、以下を行う。

1. 着地したセルを起点に、4方向(上下左右)で連結しているセルをBFS/Union-Findで走査し、連結成分(グループ)を求める。色ブロックは「同色」を連結条件とし、岩ブロックは「岩ブロックであること(hits値は問わない)」を連結条件とする(4.9)
2. 成分のサイズが4以上であれば、成分に含まれる全セルを即座に消滅させる(Emptyにする)。**色ブロックの場合のみ**1ブロックにつき30点を加算する(7章)。岩ブロックの場合は得点を加算しない(2章・4.9)
3. 成分のサイズが3以下であれば何もしない。そのセルは新しい支持構造として固定され、以後は他のブロックを支える側になる

この判定は、あるセルが実際に「落下→着地」したタイミングでのみ実行する。ランダム生成の時点でたまたま4個以上連結していた静的なブロック群は、この自動消滅の対象にはならない(プレイヤーが掘削するまでそのまま存在し続ける。4.6・4.9参照)。

### 4.6 直接掘削による即時消滅(1.の確定事実)

プレイヤーが色ブロックを掘削(1章のMoveLeft/MoveRight/Drill経由)すると、その掘削したセルを起点に4方向連結の同色グループをBFS/DFSで求め、**サイズに関わらず**(1個の孤立ブロックでも、既に4個以上連結した静的な塊でも)グループ全体を即座に消滅させる。1ブロックにつき10点(7章)。

```rust
pub fn drill_color_block(board: &mut Board, target: (usize, usize)) -> usize {
    let Cell::Color(kind) = board.get(target) else { return 0 };
    let group = connected_same_color(board, target, kind); // 4方向BFS
    for &pos in &group {
        board.set(pos, Cell::Empty);
    }
    group.len() // 呼び出し側が「消滅数 × 10点」を加算する(7章)
}
```

### 4.7 直接掘削(10点)と自動消滅(30点)の使い分け(本仕様上の整理)

確定事実の原文は2種類の別々の消滅トリガーを述べている。

- 「every block that Mr. Driller breaks earns you 10 points」→ **プレイヤーが直接掘削したことがトリガーの消滅**(4.6)。連結していた分も含め、消滅した全ブロックが10点/個
- 「sticking the blocks together into groups of four with strategic drilling ... earn you 30 points per block」→ **掘削で支えを外した結果、ブロックが落下して4個以上に連結し、掘削されずに自動消滅したケース**(4.5)。この場合のみ30点/個

同じ「掘削がきっかけ」でも、トリガーが直接ヒットか間接的な落下連結かで単価が変わる、という整理でこの2つの原文を矛盾なく説明できる。岩ブロックは4.9の通り自動消滅(4.5)の対象にはなるが得点計算の対象にはならず、酸素カプセル・ダイヤブロックはどちらの経路でも対象にならない(2章・7章)。

### 4.8 実装上の注意

- 連結成分の再計算は全マス走査ではなく、直前ティックで変化のあった行の周辺のみに限定するなど、コース最大1000m×幅12マス(=12,000セル)規模でも軽量に保てる設計にする
- 岩ブロックは`hits`を保持したまま落下・着地する(位置が変わってもヒット数はリセットされない)

### 4.9 岩ブロック(Xブロック)の連結・自動消滅・連鎖破壊(TERM独自の設計判断)

本章冒頭の確定事実1〜3は原文では色ブロックについてのみ述べているが、TERM独自の設計判断として岩ブロックにも同じ4方向連結ルールを適用する。2章で定めた「岩ブロックは掘削可(累積5ヒットで破壊)」という耐久ルール自体は変更しない。

- **連結条件**: 岩ブロック同士は、個々の`hits`値(0〜4)に関わらず「岩ブロックであること」だけで4方向連結の対象になる。ヒット数が違っていても連結は成立する(色ブロックの「同色」に相当する条件が岩ブロックでは単に「岩であること」になる)
- **落下・着地・自動消滅(4.2〜4.5と同じ枠組み)**: 岩ブロックも支えを失えば4.3の揺れを経て1マスずつ落下し、支持されている岩ブロックに接触すると停止・連結する。着地した結果の連結成分が4個以上になれば、掘削されなくても自動的に消滅する。ただし**得点は発生しない**(2章・7章。`auto_vanished_rock_blocks`のように色ブロックの自動消滅カウンタとは別に集計し、スコア加算には使わない)
- **直接掘削による連鎖破壊**: プレイヤーが岩ブロックを掘削し、そのセルの累積ヒット数が5回目に達して破壊される瞬間、そのセル単独ではなく、その時点で4方向連結している岩ブロック全部(hits値を問わない)を色ブロックの直接掘削消滅(4.6)と同様にまとめて消滅させる。連結して巻き込まれた岩ブロックがそれぞれ何ヒット目だったかは問わない
- **酸素ペナルティは1回分のみ**: 上記の連鎖破壊が起きても、酸素-20%(2章・6章)のペナルティは「実際にプレイヤーが掘削して5回目のヒットを与えた1ブロック分」としてのみ適用する。連結して巻き込まれた分に追加のペナルティは発生しない
- 岩ブロックは連結・落下・着地・連鎖破壊のいずれの場面でも`hits`を保持したまま移動する(4.8と同じ)

## 5. 押し潰し判定

- 4.4の手順4で「セルが1マス下へ移動した」際、移動先がプレイヤーの現在位置と一致するかどうかを判定する
- 一致していれば、その瞬間にプレイヤーは押し潰され、1ライフを失う(8章)。移動アニメーションの猶予やワンテンポの回避猶予は無い
- 押し潰した側のブロックは、潰された様子が見えるようその場に残したまま「天に召される」演出(9.5)へ入り、演出の完了と同時に消滅する(Emptyになる。得点は発生しない)。ライフが残っていればその位置のまま酸素を全回復して再開し、最後のライフだった場合は演出の完了と同時にゲームオーバーになる(8章)。ライフの残りによって演出の有無は変わらない
- 判定順序のまとめ:
  1. 支持判定(4.2)ではプレイヤー位置を「空洞」として扱う(プレイヤーがいても塊は落下できる)
  2. 落下先確定後、その落下先とプレイヤー位置が重なっていれば押し潰し確定
  3. 揺れ状態(4.3)のセルはまだ実際に落下していないため、この時点では判定対象にならない
- ライフ喪失後の扱い(全ライフ消費でゲームオーバーになる場合を含む)は8章を参照
- (TERM独自の設計判断)ライフを消費して再開した直後は、`INVULNERABILITY_TICKS`(13章)の間だけ押し潰し判定を無効化する。再開直後に立て続けに被弾してライフを溶かす事故を避けるための猶予である

## 6. 酸素ゲージ

| 項目 | 値 |
|---|---|
| 最大値 | 100 |
| 自然減少速度 | 1秒あたり2.0(フレーム経過時間に応じて連続的に減少させる。`oxygen -= 2.0 * delta_seconds`) |
| 酸素カプセル取得時 | +50(上限100でクランプ。既に100の場合は超過分切り捨て) |
| 岩ブロック破壊時のペナルティ | -20(確定事実: "breaking an X-block consumes 20%"。上限100とは逆に、0未満にはならない) |
| 警告閾値 | 30以下で警告(骸骨アイコン+警告音。確定事実: "When the Air Meter drops below 30%") |

- 内部値はf32で保持し、表示は整数値に切り捨てる(端数で「残り1」のような表示になるのを避けるため)

- ライフを消費して再開した際は、その時点で酸素を100へ全回復する(8章)。これは道中の自動回復とは異なり、ミス後のリスタートに限った回復である

## 7. レベル進行とスコア

確定事実として確認できたのは「100フィート(約30m)ごとに1レベルとして扱う」という進行の区切りのみである。レベル到達時に酸素が自動回復する、あるいはタイムボーナスが加算されるという記述は確認できなかったため、「200mごとのチェックポイントで酸素全回復+タイムボーナス」という方式は採らず、レベル進行とスコアを以下のとおり定義する。

### 7.1 レベル進行

- `LEVEL_STEP_M` = 30(100フィート ≈ 30.48mを30mに丸めた実装値。13章)
- レベル番号 = `(depth_m - 1) / LEVEL_STEP_M + 1` (整数除算)。深度1〜30mがレベル1、31〜60mがレベル2、というように区切る
- レベル到達は**進行状況の表示のみ**に使う(9章のステータスパネルに`LEVEL n`として表示する)。酸素回復・スコア加算は一切発生しない
- 1000mコースはレベル1〜33(30m刻み)+末尾の端数レベル(991〜1000mの10m分)、500mコースはレベル1〜16+末尾の端数レベル(481〜500mの20m分)になる

### 7.2 スコア構成要素

確定事実に基づく得点は以下の3種類のみ。

| 得点源 | 単価 | 備考 |
|---|---|---|
| 直接掘削による消滅(4.6) | 1ブロックにつき10点 | 連結していた分も含め全消滅ブロックが対象 |
| 自動消滅(4.5、同色4個以上の落下連結) | 1ブロックにつき30点 | 掘削されずに消えた場合のみ。3個以下は加点なし |
| 酸素カプセル取得 | n個目の取得で n×100点 | 1個目100点、2個目200点、3個目300点…(累積ではなく毎回n×100) |

これに加えて、TERM独自拡張として以下を残す。

| 得点源 | 単価 | 備考 |
|---|---|---|
| ダイヤブロック取得(TERM独自) | 即時+500点 | 初代の確定事実には存在しない要素。2章参照 |

岩ブロックの破壊(4.6・6章)は得点を生まない(酸素ペナルティのみ)。

### 7.3 スコア合計

```
スコア = Σ(直接掘削で消滅したブロック数 × 10)
       + Σ(自動消滅で消滅したブロック数 × 30)
       + Σ(n番目に取得した酸素カプセルについて n × 100)
       + 取得ダイヤ数 × 500        ← TERM独自拡張
```

- 深度到達そのものはスコアに直接加算しない。深度はレベル表示・クリア判定(8章)にのみ使う
- 経過タイムは参考情報としてステータスパネル(9章)に表示し続けるが、スコア計算には使わない

## 8. ゲームオーバー/クリア条件

### ライフ制

- ゲーム開始前に1〜5機からライフ数を選べる(確定事実: "Choose from one to five lives")。既定値は3機
- ライフを1つ失う条件: 酸素が0になる(6章) / 落下ブロックに押し潰される(5章)
- ライフを1つ消費した際、**盤面はリセットしない**。プレイヤーはその地点(押し潰された場合は押し潰した側のブロックが消えた同じマス)から、酸素を100へ全回復して再開する(確定事実)
- (TERM独自拡張)ミスの瞬間から再開までの間に「天に召される」演出(9.5)を挟む。ライフの減算・死亡地点の頭上クリア・酸素の全回復・ゲームオーバーへの遷移はいずれも演出の完了時にまとめて行う。演出中はライフがまだ減っていない
- 再開直後は`INVULNERABILITY_TICKS`(13章、TERM独自)の間だけ押し潰し判定を無効化する

### 終了条件

ミス音・ライフロス音は演出の開始時(ミスした瞬間)に鳴らし、ライフ消費とゲームオーバー遷移は演出の完了時に行う。

| 条件 | 結果 |
|---|---|
| 酸素が0になり、かつライフが残っている | ライフロス音を再生し演出へ。演出完了時に1ライフ消費し、その地点で酸素全回復して再開 |
| 落下ブロックに押し潰され、かつライフが残っている | ライフロス音を再生し演出へ。演出完了時に1ライフ消費し、その地点で酸素全回復して再開 |
| 酸素が0になり、かつライフが0(最後の1機だった) | ミス音を再生し演出へ。演出完了時にゲームオーバー(リザルト画面へ) |
| 落下ブロックに押し潰され、かつライフが0(最後の1機だった) | ミス音を再生し演出へ。演出完了時にゲームオーバー(リザルト画面へ) |
| 選択したコースのゴール深度(500mまたは1000m)へ到達 | ゲームクリア(クリアファンファーレを再生しリザルト画面へ) |

リザルト画面では最終スコア・到達深度・残りライフ数・経過タイム・(タイムアタックモードなら自己ベスト更新有無)を表示する。

## 9. TUI仕様

1論理セルは**横4文字×縦2ターミナル行**の大型セルとして描画する。1論理セルを1文字に圧縮するhalf-block方式は、盤面が縮小マップのように見えてしまうため採らない。画面全体のサイズ・ステータスパネルのレイアウト・配色もこの大型セルを前提に定める。

### 9.1 画面レイアウト(固定サイズ)

画面全体を固定サイズ`TOTAL_SCREEN_W = 74`列、`TOTAL_SCREEN_H = 32`行(目安)のフレームとして扱い、フィールド側`FIELD_PANE_W = 50`列、ステータスパネル側`HUD_PANE_W = 24`列を左右に並べる(50 + 24 = 74)。ターミナル実サイズがこれと異なる場合の扱いは9.8にまとめる。

```
+--------------------------------------------------+------------------------+

| ╭──╮╭──╮                                          | DEPTH                  |
| │RD││RD│                                          |   123 m (Lv.5)         |
| ╰──╯╰──╯          ╭──╮                            | SCORE                  |
|                    │BL│                            |   1,230                |
|   /\               │  │                            | AIR                    |
|   oo             ╭─┤  ├─╮  <- プレイヤー(9.5)     |   [########░░] 82%     |

|                                                    |   ♥ ×3                 |
| ...                                                | TIME                   |
|                                                    |   00:47                |

```

(上図は概念図。実際の1セルは4文字×2行、罫線・塗りの規則は9.2〜9.4、プレイヤーは9.5、HUDは9.7を参照)

- フィールド側は12列×可視`FIELD_VISIBLE_ROWS`行(基本値14。9.2参照)を描画する。コース全長(500行または1000行)は`Board`が常に内部データとして全行保持しており、画面に映るのはスクロールで切り出した一部だけである(全データ保持と表示範囲は別物として扱う)
- プレイヤーは常に画面内の固定位置(可視行のうち上から1/3、四捨五入で5行目相当)に表示し、掘り進むにつれてフィールド側を上方向にスクロールさせる
- ステータスパネルは深度/スコア/酸素/ライフを縦に積んで表示し、TERM独自にLEVELとTIMEを補助表示する。パネル幅24列に収まる範囲でのみレイアウトし、残り幅いっぱいに間延びさせない(9.7)

### 9.2 セルの描画方式(4文字×2行)

- フィールド幅は12列を維持し、1列あたりの表示幅を4文字にすることで`12 × 4 = 48`文字(+左右ボーダー2文字 = 50列 = `FIELD_PANE_W`)とする
- 縦方向の可視範囲は`FIELD_VISIBLE_ROWS = 14`(論理セル数)を基本値とする。ターミナル行数に換算すると`14 × 2 = 28`行(+上下ボーダー2行 = 30行)。9.1の固定フレーム高さ(32)との差分2行は、フィールドペインの上下に均等に配置する余白(背景色`LETTERBOX_BG`で埋める。9.6)として扱う
- 全1000行(または500行)のフィールドデータは`Board`側に丸ごと保持したままであり、スクロール処理が可視`FIELD_VISIBLE_ROWS`行分だけを切り出して描画する(「見せる範囲は絞り、データは全部持つ」考え方に統一する)

各セルは4列×2行=8文字ぶんのグリッドとして扱う。座標を`(term_row ∈ {0,1}, term_col ∈ {0,1,2,3})`と表記し、9.3〜9.5でこのグリッド内の各位置の文字・前景色・背景色を定める。

### 9.3 色ブロックの塊表現(接続マスク・丸み縁取り・ハイライト/陰影)

色ブロックが面としてまとまって見えるよう、隣接セルとの接続関係を4bitのマスクとして算出し、接続している方向の境界線を消す。

#### 接続マスクの算出(描画専用の判定)

```rust
struct ConnMask { up: bool, down: bool, left: bool, right: bool }

fn conn_mask(board: &Board, row: usize, col: usize, kind: ColorKind) -> ConnMask {
    let same = |r: isize, c: isize| -> bool {
        r >= 0 && (r as usize) < board.depth_rows() && c >= 0 && (c as usize) < FIELD_WIDTH
            && board.cell(r as usize, c as usize) == Cell::Color(kind)
    };
    ConnMask {
        up:    same(row as isize - 1, col as isize),
        down:  same(row as isize + 1, col as isize),
        left:  same(row as isize, col as isize - 1),
        right: same(row as isize, col as isize + 1),
    }
}
```

このマスクは**描画専用**であり、4章の「4方向連結によるゲームロジック上のグループ(BFS/Union-Find)」とは別物である(参照方向は同じ4方向同色判定だが目的が異なるため独立実装でよく、同一関数を共用しても構わない)。

#### セル内グリッドへの反映(角・辺・内部の3分類)

1セルは4列×2行の文字グリッドを持つ。高さが2行しかないため、左右の列(`term_col = 0`と`3`)は上下どちらの行も必ず「角」になり、辺の中間位置は存在しない。

| 位置 | 関係する方向 | 両方とも非接続 | 片方のみ非接続 | 両方とも接続 |
|---|---|---|---|---|
| `(0,0)` 左上角 | up, left | `╭` | up非接続→`─` / left非接続→`│` | 内部(fill) |
| `(0,3)` 右上角 | up, right | `╮` | up非接続→`─` / right非接続→`│` | 内部(fill) |
| `(1,0)` 左下角 | down, left | `╰` | down非接続→`─` / left非接続→`│` | 内部(fill) |
| `(1,3)` 右下角 | down, right | `╯` | down非接続→`─` / right非接続→`│` | 内部(fill) |
| `(0,1)` `(0,2)` 上辺 | up のみ | - | up非接続→`─` | 内部(fill) |
| `(1,1)` `(1,2)` 下辺 | down のみ | - | down非接続→`─` | 内部(fill) |

「内部(fill)」は罫線文字を描画せず、そのセルのシェーディング色(下記)を背景色にした半角スペースのみを描画する。隣のセルと塗り色が連続することで境界が消え、面として繋がって見える。

罫線文字(角・辺)は前景色に常にそのセルの`HIGHLIGHT`色を使う(面取りされた樽の縁が光を受けているような質感にする)。背景色はそのセル自身のシェーディング色と同じにする。

#### 上端・中央・下端のハイライト/陰影(シェーディング)

「同色の縦の連なり」における自セルの位置に応じて、3段階のシェーディング色を使い分ける。

```rust
enum Shading { Highlight, Base, Shadow }

fn shade(up_same: bool, down_same: bool) -> Shading {
    if !up_same {
        Shading::Highlight // 縦の連なりの最上段。上下とも非同色の孤立1マスもここに含む(上端優先)
    } else if !down_same {
        Shading::Shadow // 最下段
    } else {
        Shading::Base // 中間
    }
}
```

- `!up_same`(上が同色でない、または存在しない) → `Highlight`(明るい色調)
- `up_same`かつ`!down_same` → `Shadow`(暗い色調)
- `up_same`かつ`down_same` → `Base`(基本色調)

具体的な配色値は9.6にまとめる。この判定は視覚専用であり、4章のゲームロジック(縦の連結も同色4個以上で自動消滅する等)とは独立して構わない。

### 9.4 岩・酸素・ダイヤブロックの描画

岩・酸素・ダイヤは、9.3の接続マスク判定(色ブロックの「面」表現)は行わず、**常に4方向とも非接続(=常に角丸罫線でフルに縁取られた独立ユニット)**として描画する。周囲に同種のブロックが並んでいても縁取りは消さない(色ブロックの「面」とは視覚的に区別するため)。

これは見た目上の扱いであり、4章のゲームロジック上の連結判定とは別物である点に注意する。酸素・ダイヤはゲームロジック上も常に単独(4.1)だが、**岩ブロックは4.9の通りゲームロジック上は4方向連結・自動消滅の対象になる**。それでも見た目は色ブロックのような「面」の縁取り消去はせず、今回のイテレーションでは引き続き個々の樽が独立して並んでいるように描画する(連結の見た目表現は今回のスコープ外。9.11参照)。

内部(2行×2列=4文字)は種類ごとの記号を敷き詰める。

| 種類 | 内部記号(2行×2列) | 前景色 | 背景色 |
|---|---|---|---|
| 岩ブロック(Xブロック) | `XX` / `XX`(ヒット数に応じ一部が`*`に変化。下記参照) | `ROCK_X_FG` | ヒット数に応じ補間(9.6) |
| 酸素カプセル | `○○` / `○○` | `OXYGEN_FG` | `OXYGEN_BG` |
| ダイヤブロック | `◆◆` / `◆◆` | `DIAMOND_FG` | `DIAMOND_BG` |

罫線(角)の色は岩=`ROCK_X_FG`、酸素=`OXYGEN_FG`、ダイヤ=`DIAMOND_FG`を流用する(9.3の「罫線は常にHIGHLIGHT色」という原則をそのまま適用する)。

酸素カプセルの内部記号は、泡を思わせる`○`(白丸)とする(TERM独自の調整)。酸素カプセルは4.1の通り重力の対象ではあるが同色連結グループの対象外であり、他の色ブロックの重力落下によって誤って上書き・消滅することは無い(移動先セルが常にEmptyであることを前提に確定するため。4.4参照)。

#### 岩ブロックのヒビ表現(残り耐久に応じた見た目変化)

岩ブロックは`hits: u8`(0〜4、5回目で破壊。2章)を保持している。内部4文字を固定順`[(0,0), (0,1), (1,0), (1,1)]`とし、通常は`X`だが`hits`の数だけ先頭から`*`(ヒビ)に置き換える。

| hits | 内部表示 |
|---|---|
| 0(無傷) | `XX` / `XX` |
| 1 | `*X` / `XX` |
| 2 | `**` / `XX` |
| 3 | `**` / `*X` |
| 4(あと1発で破壊) | `**` / `**` |

背景色は9.6の`ROCK_BG_INTACT`→`ROCK_BG_CRACKED`の線形補間(`hits / 4.0`)と組み合わせ、色が明るくなる+ヒビ記号が増えるの2軸で「壊れそう」を表現する。

### 9.5 プレイヤースプライト

プレイヤーは単一文字`@`ではなく、facing(1章)に応じて変化する4文字×2行のスプライトで表現する。スプライトはプレイヤーがいる論理セル1マス分(9.2のグリッド)をそのまま置き換えて描画し、背景色はそのマスの本来の背景色(掘削直後で空洞になった位置は通常Empty=`FIELD_EMPTY_BG`)をそのまま使う。

| facing | 1行目 | 2行目 |
|---|---|---|
| `Down`(初期値) | ` oo ` | ` \/ ` |
| `Up` | ` /\ ` | ` oo ` |
| `Left` | `<oo ` | `<== ` |
| `Right` | ` oo>` | ` ==>` |

(各行はちょうど4文字。`oo`が目、矢印/山形記号`^ / \ < > =`が向いている方向を示す簡易的な輪郭)

```rust
fn player_sprite(facing: Direction) -> [&'static str; 2] {
    match facing {
        Direction::Down  => [" oo ", " \\/ "],
        Direction::Up    => [" /\\ ", " oo "],
        Direction::Left  => ["<oo ", "<== "],
        Direction::Right => [" oo>", " ==>"],
    }
}
```

前景色は`PLAYER_FG`固定。背景色はプレイヤーがいるマスの背景色をそのまま使い、スプライト専用の背景色は設けない。

#### 移動の見た目補間アニメーション(TERM独自拡張)

論理位置(row/col)は入力の確定と同時に整数マス単位で即座に切り替わるが、描画位置だけは直前の論理位置から現在の論理位置まで`MOVE_ANIM_DURATION_MS`(13章、目安100ms)をかけて線形補間する。当たり判定・掘削・落下判定は常に論理位置(整数マス)基準のままで、この補間は見た目のみに影響する。

- 移動が発生した(位置が変化した)瞬間に、その時点の位置を補間の起点として記録し、経過時間を0にリセットする
- 毎フレーム、経過時間を`MOVE_ANIM_DURATION_MS`で正規化した進捗`t ∈ [0.0, 1.0]`を求め、起点から現在位置まで`row`/`col`それぞれを線形補間した座標へプレイヤーのスプライトを描画する
- `t`が1.0に達したら補間は完了とみなし、以後は現在位置にそのまま描画する
- 1段登り(斜め移動、1章の2ステップ段差登り)のように`row`/`col`が同時に変化する場合も、両軸を同じ`t`で補間する

#### 押し潰されて死ぬ演出「天に召される」(TERM独自拡張、5章)

ミスになった瞬間から`CRUSH_ASCEND_MS`(13章、目安3000ms)のあいだ、「潰れた」見た目のスプライトが少しずつ上へ昇っていく演出を見せる。死因(押し潰し/酸素切れ/爆風)とライフの残りを問わず、常にこの演出を経由する。

- 通常のfacing別スプライトの代わりに、1行目に`×`を4つ並べ2行目を空白にした平たいスプライトを表示する(前景色は`CRUSH_FLASH_FG`)
- 演出の進捗に応じてスプライトの描画位置を上へずらす。全体で論理2セルぶん昇り、画面上端より高く昇った分は描画しない(そのまま見えなくなる)
- 演出中はプレイヤー自身の入力・自由落下・酸素減少だけを凍結する。周囲のブロックの重力処理は止めないため、プレイヤーの論理位置は押し潰された地点に固定されたままになる。その間に別の塊が同じ地点へ落ちてきても二重にライフを失わないよう、演出中は押し潰し判定を無効化する
- 押し潰した側のブロックは、潰された様子が見えるよう演出中その場に残し、演出の完了と同時に消す
- 演出の完了時に、死亡地点の頭上クリア・ライフ減算をまとめて行う。ライフが残っていれば酸素を全回復してその場で復活し、最後のライフだった場合はゲームオーバーへ移る(8章)
- GameOverオーバーレイは演出中は表示を保留し、演出が完了してから表示する
- `CRUSH_FLASH_MS`(13章、目安400ms)は「潰れた」見た目へ切り替えておく最低時間で、実際には上記の演出が続くあいだずっとこの見た目のままになる

#### 実装上の注意(背景色がセルごとに確実に反映されるようにする)

意図しない背景色が透けて見える事故を防ぐため、実装時は以下を必ず守る。

- `ratatui`の`Paragraph`/`Block`に`Style::default()`(fg/bg未指定)のまま子要素を描画すると、テキストが存在しない/短い行の余白セルは意図した色で塗られない(前フレームの内容やターミナルのデフォルト背景が透けて見える)。フィールドペイン・HUDペインの各行は必ずペイン幅ぶんの文字数(スペース埋め含む)で構成し、trailingの余白スペースにも明示的に`Style::default().bg(FIELD_EMPTY_BG)`等の意図した背景色を`Span::styled`で設定する。「文字が無い=背景色が自動で塗られる」とは考えない
- 9.8のレターボックス余白は中央配置する74×32のフレームの**外側**にあたるため、`frame.area()`全体に対して明示的に`LETTERBOX_BG`を背景にした`Block`(またはBufferへの直接`set_style`)をまず描画してから、その上に74×32のゲーム画面を重ねる。フレーム全体を塗る処理を省略すると、ターミナルのデフォルト背景色が縁に残る
- 罫線文字(9.3の`╭│─`等)や特殊グリフ(`X▲◆`等)を含む`Span`は、`Span::raw(...)`ではなく必ず`Span::styled(..., Style::default().fg(...).bg(...))`でfg/bg両方を明示する。fgのみ・bgのみを指定した`Span`が混在すると、指定していない側がデフォルト値のままになることがある

### 9.7 ステータスパネル(HUD)

深度/スコア/酸素/ライフを縦に積んで表示し、TERM独自にLEVELとTIMEを補助情報として加える。パネル幅は`HUD_PANE_W = 24`列固定(9.1)であり、`Constraint::Min(20)`のような「残り幅いっぱいに伸びる」制約は使わない(ターミナル横幅が広い環境ほどHUDの各行が不自然に間延びして見えるため)。

| 項目 | 表示例(ラベル行/値行) | 備考 |
|---|---|---|
| DEPTH | `DEPTH` / `  123 m (Lv.5)` | 現在深度。括弧内にレベル番号(7章)を併記 |
| SCORE | `SCORE` / `  1,230` | 7章のスコア合計 |
| AIR | `AIR` / `  [########░░] 82%` | ゲージ(幅固定、目安10〜14セル分)+%数値。30%未満で赤色化+骸骨アイコン表示 |
| LIVES | `LIVES` / `  ♥ ×3` | ハートアイコン1個+残ライフ数 |
| TIME(補助) | `TIME` / `  00:47` | 経過タイム。スコアには使わない参考表示 |

各項目はラベル行+値行の2行構成とし、値行の先頭に半角スペース2個ぶんのインデントを入れてラベルと視覚的に区別する。実際に使う横幅はパネル幅24列のうち20列前後に収め、左右に最低2列程度の余白を残す。`AIR`の`Gauge`ウィジェットを使う場合は幅を`Constraint::Length(20)`程度に明示固定し、パネル幅いっぱいまで自動で伸びないようにする。

### 9.8 画面サイズが目安と一致しない場合の扱い

`TOTAL_SCREEN_W = 74`・`TOTAL_SCREEN_H = 32`はあくまで目安の設計値であり、実際のターミナルサイズに応じて以下の3パターンに分岐する。

| ターミナルサイズ | 挙動 |
|---|---|
| 幅74以上 かつ 高さ32以上 | 中央に74×32の固定フレームを配置し、はみ出した余白は全て`LETTERBOX_BG`で塗りつぶす(9.6) |
| 幅50以上・高さ16以上(かつ上記条件を満たさない) | 縮退表示: フィールドペイン幅は`FIELD_PANE_W = 50`固定のまま(4×2セルのサイズは変えない)、可視行数を`FIELD_VISIBLE_ROWS = max(4, (実高さ - 2) / 2)`に縮小する。HUDペイン幅は`max(HUD_PANE_W_MIN = 16, 実幅 - FIELD_PANE_W)`。レターボックス余白は使わず実サイズいっぱいに描画する |
| 幅50未満 または 高さ16未満 | ゲーム画面を描画せず、警告メッセージのみ表示する: 「ターミナルサイズが不足しています(現在 {width}x{height} / 最小 50x16 / 推奨 74x32)。ウィンドウを広げてください」。この状態では`Quit`(Esc)入力のみ受け付ける |

- セルの表示サイズ(4文字×2行)自体は縮退表示でも変更しない。「盤面デバッガ風」の見た目に逆戻りする事故を避けるための固定方針であり、縮退させるのは常に**可視行数**または**HUD幅**のみとする
- 幅・高さの判定は`crossterm::terminal::size()`または`frame.area()`から毎フレーム取得し、リサイズに追従する

### 9.9 入力処理

- crossterm rawモードを有効化し、`event::poll`+`event::read`でノンブロッキング取得するメインループを組む(ポーリング間隔目安16〜33ms、描画フレームレート30〜60fps相当)
- キーとInputActionの対応は1章の表を参照。`KeyCode::Left/Right/Up/Down/Char(' ')/Char('p')/Char('q')`(pq大文字小文字とも受理)をハンドリングする
- 移動・掘削入力には`INPUT_COOLDOWN_MS`(13章、目安80ms)のクールダウンを設け、ターミナルのキーリピート速度差を吸収し操作速度を一定に保つ

### 9.10 レイアウト実装方針

- `ratatui::layout::Layout`で`Direction::Horizontal`、`Constraint::Length(FIELD_PANE_W)`+`Constraint::Length(HUD_PANE_W)`の2ペインに分割する(9.8の縮退表示時はHUD側を`Constraint::Min(HUD_PANE_W_MIN)`にフォールバックしてよいが、通常サイズでは固定長で構わない)
- フィールドペイン幅 = 12列×4文字+左右のボーダー分2文字 = 50列(`FIELD_PANE_W`)
- フィールドペインの高さ(ターミナル行数)から上下ボーダー2行を引き、2で割った値が可視論理行数になる(9.2、9.8)
- 74×32の固定フレームは、`frame.area()`の中央に**固定セル数**でセンタリングする専用関数で配置する。`centered_rect(percent_x, percent_y, area)`はポーズ/ゲームオーバー等のオーバーレイ表示専用とし、画面全体の固定フレーム配置には別途`centered_fixed_rect(width, height, area)`を用意する

### 9.11 今回のスコープ外(明記)

掘削・揺れ(4.3のShake状態)・落下・消滅の際の演出アニメーション(2〜3フレームにまたがる遷移表現等)は今回のイテレーションでは実装しない。論理ティックの結果(4章)を次の描画フレームでそのまま反映するだけでよい。揺れ状態のセルも、通常の支持されているセルと同じ見た目で描画してよい(専用の演出は次回以降のイテレーションで扱う)。

(TERM独自拡張として、プレイヤー自身の移動補間アニメーション(9.5「移動の見た目補間アニメーション」)と、ミス時の「天に召される」演出(9.5「押し潰されて死ぬ演出「天に召される」」)は実装済み。上記でスコープ外としているのはブロック側(掘削・揺れ・落下・消滅)の演出のみであり、プレイヤー自身の見た目には適用しない。)

## 10. サウンド仕様

rodioの`Source`トレイトを自前実装し、サイン波/矩形波をその場で生成してSE・BGMを鳴らす。実機音源(WAV/MP3等のサンプル素材)は使用しない。

### 波形ジェネレータの実装方針

```rust
struct SquareWave {
    freq: f32,
    sample_rate: u32,
    num_sample: usize,
    amplitude: f32,
}

impl Iterator for SquareWave {
    type Item = f32;
    fn next(&mut self) -> Option<f32> {
        self.num_sample = self.num_sample.wrapping_add(1);
        let t = self.num_sample as f32 / self.sample_rate as f32;
        let phase = (t * self.freq).fract();
        Some(if phase < 0.5 { self.amplitude } else { -self.amplitude })
    }
}

impl rodio::Source for SquareWave {
    fn current_frame_len(&self) -> Option<usize> { None }
    fn channels(&self) -> u16 { 1 }
    fn sample_rate(&self) -> u32 { self.sample_rate }
    fn total_duration(&self) -> Option<std::time::Duration> { None }
}
```

- `SineWave`も同様の構造体で`amplitude * (2.0 * PI * t * freq).sin()`により実装する
- 各SEは上記の無限長Sourceに対し`.take_duration(Duration::from_millis(N))`で長さを切り、`.amplify(音量)`で音量調整、必要に応じ簡易フェードアウト(末尾数msで振幅を線形に0へ収束)をかけてクリック音(プチノイズ)を防ぐ

### SE一覧

### BGM

- 矩形波による簡易チップチューン、4小節ループ
- テンポ140BPM(1拍=約428.6ms)、1小節=8分音符8ステップの単声ベースラインを基本形とする
- 参考ノート列(実装時に耳で微調整する前提の初期値):
  - 1小節目: C4 E4 G4 E4 C4 E4 G4 E4
  - 2小節目: A3 C4 E4 C4 A3 C4 E4 C4
  - 3小節目: F3 A3 C4 A3 F3 A3 C4 A3
  - 4小節目: G3 B3 D4 B3 G3 B3 D4 B3(4小節目終端で1小節目へループ)
- 別スレッド(`std::thread::spawn`)で`OutputStream`+`Sink`を保持し、ノート列を`.append()`し続けるループ再生を行う
- 音量はBGM用Sinkで0.25前後、SE用Sinkで0.6〜0.8を目安とし、BGMがSEを埋もれさせないバランスにする(同一`OutputStream`上に複数`Sink`をぶら下げて個別音量調整する)

### サウンドON/OFF設定と永続化(TERM独自拡張)

Sキー(`ToggleSound`、1章)でSE・BGMを一括してON/OFF切り替えできる。タイトル画面・一時停止画面でのみ受け付ける(プレイ中の誤操作を避けるため)。

- OFF中はSEの再生を一切スキップし、BGMも新しいノートの再生を止める(BGMループの内部的な進行自体は止めず、再度ONにした時に途切れた小節の途中から自然に復帰する)
- 設定はOSごとのユーザーデータディレクトリ(`dirs`クレートの`data_local_dir()`)配下に`misterdrillerterm/settings.json`としてJSON形式で保存し、次回起動時に読み込んで復元する

```json
{
  "sound_enabled": true
}
```

- 保存先が解決できない・読み書きに失敗する等の場合は、既定値(ON)にフォールバックし、ゲーム自体の続行は妨げない
- タイトル画面には現在の設定状態(ON/OFF)とSキーの案内を表示する。一時停止画面のヒントにも同様に表示する

## 11. タイムアタックモード仕様

ノーマルコースと同一の盤面生成ロジック(2〜4章)・落下ロジック・押し潰し判定・酸素ルール・TERM独自拡張(ボム、アイテムブロック3種、100mチェックポイント等)をそのまま流用し、勝敗条件を「タイム」に絞ったモード。今回のスコープ外(未実装)。本章は初期企画時の設計を、その後実装されたTERM独自拡張(モードセレクト#112・ボム#96・アイテムブロック#98/#101/#107/#210/#211・チェックポイント#178/#190・設定画面の各種調整項目)と整合するよう全面改訂したもの。

### 目的

- 盤面のランダム性による有利不利を排除し、純粋なプレイヤースキルの比較(自己ベスト更新)を可能にする
- 「ランダム性の排除」とは乱数要素(ボム・アイテム補充等)を削除することではなく、乱数の恣意性を排除すること(全ての抽選をシードから決定的に導出すること)と定義する。ボムやアイテムはタイム戦略の一部(スター化・頭上クリアによる時短)であり、無効化すると通常プレイと別のゲームになってしまうため、有効のまま決定化する

### モードの入口とコース長

- モードセレクト画面(#112)を4択に拡張する: 「イージー(500m)/ノーマル(1000m)/タイムアタック 500m/タイムアタック 1000m」。既存のイージー/ノーマルの操作体系(↑↓←→で切り替え・Enterで決定・Qで戻る)を引き継ぐ
- タイムアタックは500m/1000mの両コースで遊べ、自己ベスト記録はコース長ごとに独立したレコードとして保存する(コース長が違えばタイムは比較不能のため)
- 500mコースではゴール(500m)とボーナスフロア深度(`BONUS_FLOOR_DEPTH_M` = 500m)が一致するためボーナスフロアは発生しない。1000mコースでは通常プレイ同様に500mボーナスフロアが発生する(#179。ただし後述の通り抽選は決定化する)
- 前回の選択は`settings.last_course_depth_m`(既存)に加え、タイムアタック選択の有無を`last_mode_time_attack`(bool)として設定ファイルへ保存し、次回モードセレクトの初期カーソルに反映する
- フレーム巻き戻し(16章)はタイムアタック中は**無効**にする。過去へ戻ってやり直せるとタイムの比較が成立しないため、Backspace/Uの入力自体を無視する(HUDのストック表示も出さない)

### 固定シード

- タイムアタックモードは常に固定シード `TIME_ATTACK_SEED: u64 = 0x4D444C31_54494D45`(ASCIIで"MDL1TIME"。10進では5567658814087974213)を使用する
- `Board::generate(TIME_ATTACK_SEED, depth_goal_m, width)`自体は決定的だが、現在の実装ではこれだけでは同一盤面にならない。新規ゲーム開始時に必ず実行される配分率反映(`Game::reroll_spawn_rates_from` → `Board::reroll_overlays_in_row_range`)・アイテム窓補充(`Board::top_up_items`)・500mボーナスフロア再抽選が、いずれも`rand::rng()`(OS乱数)から呼び出しごとに新しい乱数系列を作るためである。次節の決定化が本モード成立の前提条件となる

### 乱数の決定性(シード派生RNG・セル位置ハッシュ)

全ての乱数消費点を「ゲームシード + 用途別salt + 文脈キー」から決定的に導出する方式へ変更する。導出には単純なミキサ(SplitMix64等)を使い、用途saltは定数として13章の定数一覧に追加する。

- **盤面の抽選(基底シード注入 + セル位置ハッシュ)**: `Board::reroll_overlays_in_row_range`と`Board::top_up_items`は「関数冒頭で単一のRNG系列を作る」現行方式をやめ、引数で受け取る`base_seed: u64`とセル座標から `mix(base_seed, row, col)` でセルごとにRNGを導出する方式に変更する
  - 通常プレイ: 呼び出し側が従来通り`rand::rng()`で`base_seed`を作って渡す。呼び出しごとに系列が変わるという現行の性質(「再現性は求めない」)はそのまま保たれ、通常プレイの体感は変わらない。コードパスも1本で済む
  - タイムアタック: `base_seed = mix(TIME_ATTACK_SEED, SALT_用途)` を渡す(開始時の配分反映=`SALT_OVERLAY`、ボーナスフロア=`SALT_BONUS_FLOOR`、アイテム補充=`SALT_ITEM_TOP_UP`)
  - セル位置ハッシュにする理由: 現行実装はEmpty/Itemセルを抽選せずスキップするため、呼び出し単位でシードを固定するだけでは「どのセルが掘削済みか」(=プレイ内容)によって乱数消費がずれ、後続セル全部の結果が変わってしまう。セルごとに独立導出すれば、未掘削セルの抽選結果はプレイ経過・呼び出しの区切り方(補充が何行ずつ走ったか)に依存しない
- **ボム**: 出現判定・出現位置・登場方向の抽選を`Game::rng`から専用の`bomb_rng`へ分離する(タイムアタックでは`mix(seed, SALT_BOMB)`で初期化。通常プレイはOS乱数で初期化してよい)。出現判定は既に固定間隔(`BOMB_SPAWN_CHECK_INTERVAL_MS`)のアキュムレータで行われているため、分離すれば判定系列はゲーム内経過時間に対して決定的になる。現行は着地バウンド方向や色統一先と同じ`self.rng`を共有しており、プレイ内容で消費順がずれる
- **効果系の抽選**(アイテム「色統一」の統一先色など、盤面抽選以外でプレイ結果に影響する乱数): タイムアタックでは `mix(seed, SALT_用途, そのゲーム内での使用回数)` で導出する。演出のみに影響する乱数(バウンド方向等)は決定化不要
- **決定性の保証水準**(仕様として明文化する):
  - 保証(強): 開始時点の盤面(岩/AIR/スター/ダイヤ/色/アイテムの初期配置)は毎回完全に同一
  - 保証(中): アイテム補充・ボーナスフロア再抽選・ボム出現判定・効果系抽選の乱数系列はシード由来であり恣意性がない。同一の入力列でプレイすれば同一の結果になる
  - 非保証: プレイ内容が異なれば動的要素の帰結は変わる(補充対象となる未掘削セルの残り方、ボム設置候補のEmptyマス、窓内のアイテム残数=補充数など)。これは乱数の不公平ではなくプレイの帰結として許容する

### レギュレーション(設定の固定)

- タイムアタック中は、盤面・難易度に影響する設定を全て既定値(13章の定数一覧・`settings.rs`のDefault実装)に固定する: 岩/AIR/スター/ダイヤ/アイテム3種/ボムの出現率(いずれも100%)・ボム爆発までの時間(`BOMB_FUSE_MS`)・色数(4)・色ブロックの結合率(100%)・フィールド幅・ブロック落下/プレイヤー落下/揺れ/回避/移動クールダウン/連鎖消滅間隔の各速度パラメータ。`settings.json`の値は参照しない
  - 理由: 自己ベストの比較可能性を守るため。設定の組み合わせごとに別レコード管理する案(設定ハッシュをレコードキーに含める)は、レコードが無限に分裂して「自己ベスト」の意味が薄れるため採用しない
- ポーズ中の設定オーバーレイは開けるが、上記の項目はロックし変更操作を無視する(項目に「TIME ATTACKでは固定」の旨を表示)。MUSIC/SE・デバッグログのトグルはプレイに影響しないため変更可
- デバッグショートカット(C/R/K/L/A/B/O/[/]/-/=/,/.)はタイムアタック中すべて無効化する(入力を無視する。効果はアイテムブロックの取得によってのみ発動する)

### 計測方法

- ゲーム開始(モードセレクトで決定しPlayingへ遷移した瞬間)から、ゴール深度到達(`GameStatus::Cleared`)またはライフを使い切っての終了までの経過時間をミリ秒単位で計測する
- 計時は`player.elapsed_seconds`(f32秒。演出用)とは別に、専用の`elapsed_play_ms: u64`を`update()`のdeltaミリ秒で累積して行う(f32の丸め誤差蓄積を避け、ミリ秒精度の記録を保証するため)。加算は`GameStatus::Playing`中のみ(ポーズ・ゲームオーバーダイアログ・クリア後は停止)
- カウントダウン演出は初版では入れない。固定シードにより盤面は既知(リトライして覚える前提)であり、開始前の閲覧時間を厳密化する意味が薄いため。将来の演出拡張として妨げない
- ライフ切れで終了した場合は「未完走」として記録し、自己ベストの更新対象にしない(完走タイムのみを比較対象とする)
- HUDのTIME表示はタイムアタック中のみ`MM:SS.mmm`のミリ秒精度にする(通常プレイは既存の`MM:SS`のまま)。7章のスコア計算はタイムアタックでも通常通り計算し参考表示するが、モードの主目的はタイムそのものである

### ポーズ・リトライ・復活の扱い

- ポーズは可能で、ポーズ中は計時を停止する。ただし停止中に盤面を見ながら長考できてしまうため、タイムアタック中のポーズは盤面を隠す(HUDとPAUSE表示のみ残す)
- ゲームオーバーダイアログの「その場から復活(Revive)」はタイムアタックでは提供せず、選択肢を「リトライ/タイトルへ戻る」に差し替える。リトライは同一シード・同一レギュレーションで即座に最初からやり直す(挑戦回数は+1)
- クリア後のリザルトにもリトライ導線を置く(連続挑戦がこのモードの基本ループのため)

### 自己ベスト記録の保存

- OSごとのユーザーデータディレクトリ(`settings.rs`と同じ`dirs`クレートの`data_local_dir()`)配下に`misterdrillerterm/time_attack_best.json`として保存する
- 保存内容(コース長ごとに独立したレコード):

```json
{
  "regulation_version": 1,
  "seed": 5567658814087974213,
  "courses": {
    "500":  { "best_time_ms": 98342,  "achieved_at": "2026-08-27T12:34:56+09:00", "attempts": 4 },
    "1000": { "best_time_ms": 187342, "achieved_at": "2026-08-27T12:34:56+09:00", "attempts": 12 }
  }
}
```

- `seed`は固定値だが、将来シードを変更した場合に旧記録と混同しないよう記録に含めておく。`regulation_version`は「タイムの比較可能性を壊す変更」(盤面生成ロジック・乱数導出方式・レギュレーション既定値の変更等)を入れた際にインクリメントする。読み込み時に`seed`または`regulation_version`が現行と不一致なら全レコードをリセットする
- クリア(ゴール深度到達)する度に該当コースの`best_time_ms`と比較し、更新されていれば上書き保存。`attempts`は挑戦回数(クリア/ライフ切れ/リトライ問わず、そのコースのタイムアタックを開始した回数)をインクリメントする
- ファイルの読み書きは`settings.rs`と同じ方針に合わせる(一時ファイルへ書き込んでからrename、破損・欠損時は既定値へフォールバック)
- リザルト画面で「自己ベスト更新」の有無と、更新した場合は旧ベストとの差分(短縮ms)を表示する

## 12. ネットワーク対戦モード仕様

次フェーズの実装者がそのまま実装に落とせる粒度で、UDPブロードキャストによる対戦相手自動探索→TCP接続→lockstep同期の全手順を規定する。今回のスコープ外(未実装)。

本章は当初、通常プレイのコアシステムのみが存在した時点で書かれた。その後のTERM独自拡張(ボム#96、アイテムブロック3種#98/#101/#107/#210/#211、100mチェックポイント#178/#190、モードセレクト#112、設定画面の配分率調整等)により、一時「同一シードなら両者の盤面・進行が完全一致する」というlockstepの前提が崩れる懸念があったが、#221(2026/09/12)でこの改修を実施済みで、現在は前提が成り立っている(詳細は12.6)。

### 全体フロー概要

```
[起動・対戦モード選択]
        |
        v
[UDP: HELLO を1秒間隔でブロードキャスト送信 + 受信待ち]
        |  (他ホストのHELLOを受信して候補リストに表示)
        v
[プレイヤーが候補を選びINVITE送信] --> [相手がACCEPT/DECLINEを返す]
        |  (ACCEPT)
        v
[UDPブロードキャスト停止]
        |
        v
[TCP接続確立(ACCEPT側がlisten、INVITE側がconnect)]
        |
        v
[TCPハンドシェイク: Hello交換 → StartConfig(ホスト設定の強制適用) →
 シード決定(SeedAgree) → StartCountdown]
        |
        v
[lockstep対戦ループ: 毎tickInput交換 → 両者が確定的にシミュレーション
 (各ホストは自分+相手の2つのGameインスタンスを並行シミュレーション) →
  定期StateHash照合]
        |
        v
[先にゴール深度到達 or 脱落 or 切断 → Result交換 → 対戦終了]
```

### 12.1 UDPブロードキャストによる自動探索

(本節はTERM独自拡張の実装後も変更なし)

#### ポート番号

| 用途 | プロトコル | ポート |
|---|---|---|
| 対戦相手探索(HELLO/INVITE/ACCEPT/DECLINE/BYE/REQUEST_START) | UDP | 39393 |
| ゲーム開始後の本接続(既定値。実際に使う値はHELLOパケットで相手に通知する) | TCP | 39394 |

- ブロードキャスト送信先は`255.255.255.255:39393`(サブネット限定ブロードキャストが必要な環境向けに、各ネットワークインターフェースのIPv4アドレスから求めた directed broadcast アドレスへ個別送信するフォールバックも実装しておくことが望ましい)
- ソケットは`SO_BROADCAST`を有効化し、同一ポートで送信と受信の両方を行う(`UdpSocket::bind("0.0.0.0:39393")`)

#### パケットフォーマット(固定長60バイト、リトルエンディアン)

| オフセット | サイズ | フィールド | 内容 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `"MDT1"` (0x4D 0x44 0x54 0x31)。プロトコル識別子 |
| 4 | 1 | packet_type | u8。下記「パケット種別」参照 |
| 5 | 1 | protocol_version | u8。現在は`1`固定(本章の改訂内容を初版プロトコルとする。旧版の実装は存在しないため互換性負債はない) |
| 6 | 16 | sender_id | 送信者のプレイヤーID(UUID v4の生バイト列。起動時に1回生成しセッション中固定) |
| 22 | 16 | target_id | 宛先プレイヤーID。HELLO/BYEでは全ゼロ固定。INVITE/ACCEPT/DECLINEでは相手のsender_idを指定 |
| 38 | 16 | player_name | 表示名。UTF-8バイト列を16バイトに収め、余りは`0x00`でパディング(16バイト超は切り詰め) |
| 54 | 2 | tcp_port | u16。このホストがゲーム開始後にlistenするTCPポート(既定`39394`。使用中なら`39395`, `39396`…と1つずつ空きを探して採用する) |
| 56 | 4 | reserved | 将来拡張用。送信時は全`0x00`、受信時は無視する |

合計: 60バイト固定長。

#### パケット種別(packet_type)

| 値 | 名称 | 意味 | target_id |
|---|---|---|---|
| 0x01 | HELLO | 生存/募集アナウンス。1秒間隔で送信し続ける | 全ゼロ |
| 0x02 | INVITE | 対戦招待 | 招待相手のsender_id |
| 0x03 | ACCEPT | 招待受諾 | 招待者のsender_id |
| 0x04 | DECLINE | 招待拒否 | 招待者のsender_id |
| 0x05 | BYE | 探索/募集からの離脱通知(候補リストからの即時除去用) | 全ゼロ |
| 0x06 | REQUEST_START | ゲストからホストへの開始要求。ホストは追認せず即座に開始する(#293) | ホストのsender_id |

#### 候補リストの管理

- 自ホストと異なる`sender_id`のHELLOを受信するたびに、候補リスト(`sender_id -> (player_name, ip_addr, tcp_port, 最終受信時刻)`)を更新する
- 最終受信から5秒(`DISCOVERY_TIMEOUT_MS` = 5000)経過した候補は一覧から自動的に除去する
- BYEを受信した場合は即座に該当候補を除去する

#### 招待から接続確立まで

1. プレイヤーがTUI上で候補を選びEnterすると、選んだ相手の`sender_id`を`target_id`に設定したINVITEを送信し、応答待ち状態(タイムアウト`INVITE_TIMEOUT_MS` = 10000)に入る
2. 招待された側はINVITEダイアログを表示し、Y(承諾)/N(拒否)で応答する
   - Y: `target_id`=招待者の`sender_id`としたACCEPTを返す。自身は以後TCPサーバ役として、自分のHELLOで広告した`tcp_port`で`TcpListener::bind`しlistenを開始する
   - N: DECLINEを返し、探索状態を継続する
3. INVITEを送った側がACCEPTを受信したら、UDPブロードキャスト送信を停止し、ACCEPTの送信元IPアドレス＋そのホストが最後に広告していた`tcp_port`へ`TcpStream::connect`する(=INVITE側がクライアント役)
4. 3秒(`TCP_CONNECT_TIMEOUT_MS` = 3000)以内に接続確立できない場合は対戦不成立とし、双方ともUDP探索状態(HELLO再送)へ戻る

### 12.2 TCP接続確立後のゲーム開始シーケンス

TCP接続後は、4バイトのビッグエンディアン長さプレフィックス(u32、以降のペイロードのバイト数)+ペイロードでフレーミングする。ペイロードは`serde`+`bincode`でシリアライズする。

```rust
#[derive(Serialize, Deserialize)]
enum GameMessage {
    Hello { name: String },
    /// ホスト(TCPサーバ役)のシミュレーション影響設定一式。クライアントは
    /// この値を対戦セッション中のみ強制適用する(自分のsettings.jsonへは保存しない)。
    StartConfig(BattleConfig),
    SeedAgree { seed: u64 },
    StartCountdown { start_at_unix_ms: u64 },
    Input { tick: u32, action: InputAction },
    Heartbeat { tick: u32 },
    /// 定期デシンク検出(12.3)。互いのシミュレーション状態のダイジェストを照合する。
    StateHash { tick: u32, local_hash: u64, remote_hash: u64 },
    Result { reached_goal: bool, tick: u32, time_ms: u64 },
    Bye,
}

/// シミュレーション結果に影響する設定の完全な集合(TERM独自拡張の設定画面項目
/// のうち、music/SE/debug_log等のローカル専用項目を除く全て)。ホスト側の
/// settings.rsの現在値をそのまま詰める。1つでも食い違うと決定性が崩れるため、
/// 「両者で揃える」のではなくホストの値を一方的に採用する。
#[derive(Serialize, Deserialize)]
struct BattleConfig {
    /// 対戦のゴール深度(m)。ホストがモードセレクト(#112)で選んだコースに従う。
    /// 既定はイージーコース(COURSE_EASY_DEPTH_M = 500)。初期実装はUI上500m固定でよいが、
    /// プロトコル上はこのフィールドで1000m対戦へ拡張できる。
    depth_goal_m: u32,
    field_width: u32,
    rock_spawn_rate_percent: u32,
    air_spawn_rate_percent: u32,
    star_spawn_rate_percent: u32,
    diamond_spawn_rate_percent: u32,
    item_clear_above_rate_percent: u32,
    item_unify_colors_rate_percent: u32,
    item_starify_screen_rate_percent: u32,
    color_count: u8,
    color_cluster_rate_percent: u32,
    bomb_spawn_rate_percent: u32,
    bomb_fuse_ms: u32,
    attack_blocks_per_rock: u32,
    attack_rocks_per_wave_max: u32,
    block_fall_tick_ms: u64,
    player_fall_tick_ms: u64,
    shake_duration_ms: u64,
    move_cooldown_ms: u64,
    dodge_recovery_ms: u64,
    chain_vanish_interval_ms: u64,
}

/// 1章のInputActionのうちネットワーク同期に必要な要素のみを送る。
/// TogglePause/Quit/ToggleMusic/ToggleSe/Debug*系はローカルのみで完結させ
/// (12.5の通り対戦中はほぼ無効化)、対戦tickには含めない。
#[derive(Serialize, Deserialize, Clone, Copy)]
enum InputAction {
    None,
    MoveLeft,
    MoveRight,
    FaceUp,
    FaceDown,
    Drill,
}
```

シーケンス:

1. 接続確立直後、両者が`Hello { name }`を送り合い、相手の表示名をTUIに反映する
2. **TCPサーバ役(ACCEPTした側)=ホスト** が`StartConfig(BattleConfig)`を送信する。クライアントは受信した設定を対戦セッション中のゲーム生成・進行にのみ適用する(自分の`settings.json`は書き換えない。対戦終了後は自分の設定へ戻す)
3. ホストがOS乱数から64bitのシードを生成し、`SeedAgree { seed }`をクライアント役へ送信する。クライアント役はこの`seed`をそのまま採用する(=両者は必ず同一シードを使用する。ホストが単独決定することで「どちらのシードを使うか」の合意プロトコルを省略している)
4. 両者は、`BattleConfig`と`seed`から**完全に同一の手順**で、**2つの`Game`インスタンス**(自分用と相手用。12.3参照)をそれぞれローカルに生成する。生成手順は通常プレイの開始処理と同一順序に固定する:
   1. `Game::new_with_width(seed, config.field_width, config.depth_goal_m)`
   2. `set_block_fall_tick_ms`等、`BattleConfig`の速度系設定の反映
   3. `reroll_spawn_rates_from(2, ...)`(配分率・色数の反映。12.6の決定的乱数ストリームを使用)
   この時点で4つのインスタンス(各ホスト2つ)の盤面は完全一致するはずであり、以後は入力のみで状態が分岐しないようにする(12.6)
5. ホストが`StartCountdown { start_at_unix_ms }`(現在時刻+3000ms程度)を送信し、両者はローカルの時計でその時刻になるまで「3, 2, 1, GO」のカウントダウンをそれぞれ独立表示してから対戦を開始する(NTP的な厳密同期は行わず、この程度の簡易同期で十分とする)
6. 対戦開始後は12.3のlockstepループに入る

### 12.3 lockstep方式での盤面同期

#### 基本方針

- 対戦は固定の論理tick(`NET_TICK_MS` = 150ms)で進行する。**通常プレイの`FALL_TICK_MS`と同値だが別定数として定義する**(`block_fall_tick_ms`等は設定・デバッグ操作で可変になったため、「落下tick」と「ネットワークtick」はもはや同一概念ではない。落下速度等の設定値は`Game::update`内部のサブタイマーとしてネットワークtickの中で決定的に消化される)
- **各ホストは`Game`インスタンスを2つ保持する**: 自分の盤面(`game_local`)と相手の盤面(`game_remote`)。両方を毎tick同じ手順で進めることで、(a)相手の盤面・深度をリアルタイム表示できる、(b)勝敗判定を相手からの自己申告に頼らず自分のシミュレーションで独立に検証できる。相手盤面の表示は縮小表示や深度・ライフ・進捗バーのみの簡易表示でもよいが、**シミュレーション自体は省略してはならない**
- 各tickで両者はその瞬間の自分の入力(何もしていなければ`InputAction::None`、**1tickにつき高々1アクション**)を確定し、`Input { tick, action }`として相手に送信する
- 自分のtick分の入力を確定させると同時に、相手から届いた同じtick番号の`Input`を待つ。**両者の当該tickの入力が揃って初めて、そのtickのシミュレーションを実行する**。実行内容は両インスタンス共通で次の固定順序とする:
  1. `game_local`へ自分のアクションを適用(`try_move_left`等。`None`なら何もしない)
  2. `game_remote`へ相手のアクションを適用
  3. `game_local.update(Duration::from_millis(NET_TICK_MS))`を1回呼ぶ
  4. `game_remote.update(Duration::from_millis(NET_TICK_MS))`を1回呼ぶ
  `update`へ渡すデルタを実測経過時間ではなく**常に150ms固定**にすることが決定性の核であり、移動クールダウン(80ms)・ボム出現判定(1000ms蓄積)・酸素減少・揺れ→落下・連鎖消滅・チェックポイント処理・アイテム窓補充など、実装内の全サブタイマー/乱数消費が両ホストで同一に進む
- 乱数はシード共有された決定的ストリーム(12.6)のみを使用するため、同一シード+同一入力列から両者は必ず同一の状態遷移をたどる
- 相手の入力が届かない場合は最大500ms(`LOCKSTEP_WAIT_TIMEOUT_MS`)待機する。タイムアウトした場合は相手の切断とみなし対戦を中断する(相手の不戦敗扱い)

#### デシンク検出(StateHash)

- TERM独自拡張によりシミュレーションの状態量が大きく増えた(ボム・アイテム窓・チェックポイント・演出タイマー等)ため、実装バグによる非同期(デシンク)の早期検出機構を必須とする
- 各ホストは`STATE_HASH_INTERVAL_TICKS`(= 20 tick、約3秒)ごとに、自分が持つ2インスタンスそれぞれの状態ダイジェスト(u64)を計算し、`StateHash { tick, local_hash, remote_hash }`として送信する
- ダイジェストは、シミュレーション結果を代表する正準値列 — 盤面全セル、プレイヤーの(row, col, facing, lives, depth)、酸素ゲージのビットパターン(`f32::to_bits`)、スコア、盤上のボム(位置・残りタイマー)、`item_top_up_frontier_row`、対戦の妨害ルール(12.8)の状態(`attack_power_pending`・`incoming_attack_power`・`incoming_rocks`の各要素の位置と残り時間) — をFNV-1a(64bit)で順にハッシュした値とする。演出専用フィールド(フラッシュ残時間・描画補間等)は含めない
- 受信した相手の`StateHash`と自分の対応するtickの値を照合し、不一致なら**デシンクとして対戦を中断し、引き分け扱い**とする(どちらの状態が正かは判定不能のため)。TUIにはデシンク終了である旨を表示する

#### ネットワーク遅延対策(将来拡張)

- 初期実装では上記の「揃うまで待つ」素朴な同期で問題ない(対戦専用LANが前提のため遅延は小さい)
- 体感遅延が問題になる場合は、入力を1〜2tick先行してバッファする「入力遅延バッファ方式」への拡張を想定しておく(本仕様のtick番号付きInputメッセージはそのまま流用できる設計にしてある)

#### 通常プレイとの操作感の違い(明記しておく仕様上の注意点)

- 通常(1人プレイ)モードの移動・掘削は押下即座に反映される(実測フレーム間隔でクールダウン80msが消化される)のに対し、対戦モードは入力が150ms周期のtickに量子化される(実効的な連打上限も1tick1アクションに制限される)。これは決定論的シミュレーションを成立させるための意図的な仕様差であり、実装漏れ・バグではない

### 12.4 対戦ルールと決着判定

勝敗条件に加え、両者は12.8の妨害ルール(攻撃力→岩投下)で互いの盤面に干渉する。決着判定自体は変わらない。

- 両者は同一シード・同一設定(`BattleConfig`)で生成された同一盤面を、同時にスタートしてそれぞれ独立に掘り進む。なお、アイテムブロック3種は各プレイヤーの進行に追従する窓単位補充(#210/#211)のため、対戦が進むにつれ両者の盤面上のアイテム配置は(互いの掘り方の違いを反映して)一致しなくなるが、これは同一の決定的規則が各盤面へ独立に適用された結果であり、デシンクではない(各ホストが持つ同一プレイヤーのインスタンス同士は常に一致する)
- **ゴール深度(`BattleConfig.depth_goal_m`、既定500m)へ先に到達した方の勝ち**とする。既定値はモードセレクト(#112)のイージーコース(`COURSE_EASY_DEPTH_M` = 500)と同一。500m対戦では、500m地点のボーナスフロア(#179)は「ゴール=500m」のため通常プレイのイージーコースと同様に発生しない(既存実装の挙動のまま)。1000m対戦へ拡張した場合は500mボーナスフロアも両者に同一内容で出現する(12.6の決定化が前提)
- 到達判定・脱落判定は両ホストが自分の持つ2インスタンスから**独立かつ同一に**導出できる(12.3)。`Result`メッセージは判定の根拠ではなく相互確認用とする: 自分側インスタンスが確定した時点で`Result { reached_goal, tick, time_ms }`(tick=確定tick番号、time_ms=`start_at_unix_ms`からの経過)を送信し、相手の`Result`または自分のシミュレーション結果と照合する。食い違った場合はデシンクと同様に引き分け扱いとする
- 勝敗は確定tick番号の早い方を勝者とする。同一tickで両者が同時にゴール到達した場合は引き分けとする
- どちらかがライフを使い切って脱落(GameOver)した場合は生存側の勝ちとする。両者が同一tickで同時に脱落した場合は引き分けとする。**通常プレイのGameOverダイアログ(タイトルへ戻る/その場から復活)は対戦では表示せず、「その場から復活」(Revive)は使用不可**(脱落=即敗北確定)
- 対戦中にTCP接続が切断された場合、切断を検知した側の不戦勝とする(検知はソケットエラーまたはHeartbeatの`HEARTBEAT_TIMEOUT_MS`(目安2000ms)超過で行う)

### 12.5 対戦モードで無効化・固定化する機能

TERM独自拡張のうち、以下は決定性・公平性を壊すため対戦中は無効化する:

| 機能 | 通常プレイ | 対戦モード |
|---|---|---|
| P(一時停止) | Playing⟷Paused切替 | **無効**(片側だけ止まるとlockstepが破綻する。離席したい場合はそのまま放置するか、Quitで不戦敗を受け入れる) |
| 設定画面からのプレイ中変更(配分率・速度・ボム率等) | 一時停止中に変更可 | **無効**(設定は`StartConfig`受領時点の値で対戦終了まで固定) |
| デバッグショートカット(ライフ+1・AIR回復・頭上クリア・スター化・ボム設置・2色統一・速度調整等) | 使用可 | **全て無効**(状態を直接書き換えるため即デシンク/チートになる) |
| GameOver時の「その場から復活」(Revive) | 選択可 | **無効**(12.4) |
| フレーム巻き戻し(Backspace/U、16章) | 使用可 | **無効**(片側だけ過去の状態へ飛ぶと即デシンクする。ローカルで状態を差し替える機能であり、lockstepの入力列では表現できない) |
| MUSIC/SEトグル | 使用可 | **使用可**(音声はローカル専用でシミュレーションに影響しないため) |
| ブロック状態遷移ログ(debug_log) | 設定で有効化可 | **使用可**(読み取り専用の記録でありシミュレーションに影響しない。デシンク調査にはむしろ有用) |

### 12.6 決定性の担保(#221で改修済み)

lockstepは「同一シード+同一入力列→同一状態」が成立して初めて機能する。かつて`reroll_overlays_in_row_range`・`top_up_items`がOSの真性乱数(`rand::rng()`)から呼び出しごとに新規シードを作っており、同一シードでも盤面が一致しない状態だったが、#221(2026/09/12、コミット`719923a`。目的はオートプレイのソークテストで失敗シードを再現するためで、対戦のためではない)でこの問題は解消済み。

#### 現状の乱数系統

| 乱数消費箇所 | 実装 | 決定性 |
|---|---|---|
| `Board::generate(seed, ...)`(初期盤面生成) | 引数`seed`の`ChaCha8Rng` | 決定的 |
| ボム出現判定・位置抽選(#96)、ボムの跳ね方向抽選(#241)、「2色統一」アイテムの色選択、相手の攻撃で降る岩の出現列抽選(#247) | `Game.rng` = `ChaCha8Rng::seed_from_u64(!seed)` | 決定的(固定デルタ前提) |
| `Board::reroll_overlays_in_row_range`(配分率再抽選。新規ゲーム開始時の設定反映・500mボーナスフロア#179が経由)、`Board::top_up_items`(アイテム窓補充#210/#211) | 呼び出し元(`Game`)から`&mut ChaCha8Rng`を受け取る形に変更済み。実際には`self.rng`(上記と同じストリーム)を渡している | 決定的 |
| `debug_unify_nearby_colors`(デバッグ専用) | `self.rng`を使用 | 決定的だが対戦では無効化(12.5)のため対象外 |

#### 採用された設計: 単一ストリームの共有(系統分離は不採用)

12.6の旧版は`terrain_rng`/`item_rng`という系統別ストリームへの分離を提案していたが、#221では**単一の`Game.rng`を全用途で共有する**形が採用された(`TERRAIN_RNG_SALT`/`ITEM_RNG_SALT`は未実装、13章の該当行は不採用として残置)。

- lockstepにとってはどちらでも問題ない。両者が同じコードを動かす以上、1本のストリームでも消費順は一致する
- 系統分離が効くのは「ボムの抽選回数を変える修正を入れても、過去のシードで地形やアイテムの並びまで変わらない」という、バージョン間のリプレイ再現性の場面のみ。対戦モードの必須条件ではないため、今回は見送られた
- 消費順序は「生成→開始時反映→以後はプレイヤー進行に伴う窓補充・チェックポイント処理→ボム/アイテム関連の各種抽選」という単線の実行順で確定するため、同一入力列なら消費列も一致する
- 改修の検証として、同一シード・同一設定・同一の固定デルタ入力列で`Game`を2インスタンス走らせて状態を突き合わせるテストが既に存在する: `src/autoplay.rs`の`replaying_the_same_seed_reproduces_the_run_exactly`(フレーム数・到達深度・岩破壊数・イベント列の一致を確認)、`src/game/mod.rs`の`assert_same_state`ヘルパー(巻き戻しの決定性テストが使用)。12.3のStateHash(状態ハッシュ)関数は`Game::state_hash`(#250)として実装済みで、同一シード・同一入力列の2インスタンス間で毎tick一致することをテストで確認している(通信層(#10本体)が実装されるまではテストからのみ呼ばれる)

#### 浮動小数点の決定性(注記)

シミュレーションは`f32`(酸素・深度カーブ・経過秒)を含むが、使用しているのは四則演算・比較・`clamp`のみで超越関数は無い。IEEE754準拠環境(x86_64/aarch64のRustターゲット)ではこれらの演算結果はビット単位で一致するため、クロスプラットフォーム対戦でも問題にならない。将来ロジックへ`sin`/`powf`等のlibm依存関数を追加する場合は対戦同期への影響を検討すること。

### 12.7 実装メモ

- ネットワーク送受信は専用スレッド(`std::thread::spawn`)を立て、`std::sync::mpsc`チャネルでメインのゲームループ(TUI描画・入力処理)と受け渡す設計とし、既存のratatui同期描画ループをブロックしないようにする
- lockstepのtick進行(150ms)と描画フレームは独立させる。描画は毎フレーム行ってよいが、`Game::update`の呼び出しはtick確定時(両者のInputが揃った時)のみとする
- `uuid`クレートで`sender_id`/`target_id`用のUUID v4を生成する
- パケットの`player_name`フィールドはUTF-8のマルチバイト文字境界で切り詰めないよう、切り詰め処理はchar境界を考慮して実装する

### 12.8 対戦の妨害ルール(攻撃力と岩の投下)

対戦は同一盤面を別々に掘るだけでなく、消したブロック数を攻撃力として相手の盤面へ岩(Xブロック)を降らせ合う。通信層(12.1〜12.3)より先にゲームルールだけを実装してあり、ローカルでデバッグショートカットから動作を確認できる。

#### 攻撃力の計測

- 攻撃力は**自分が消したブロック数の単純合算**とする。倍率・連鎖ボーナスは付けない
- 数える対象は次の2系統のみ
  - 直接掘削による消滅(4.6): 色ブロック(連結して巻き込んだ分を含む)、岩ブロック(1回の掘削で壊れるのは1個)、スターブロック(1個)
  - 着地時の4連結以上の自動消滅(4.5・4.9): 色ブロック・岩ブロックの両方
- ボムの爆風で消えた分(15.4)は数えない
- スコアとは別勘定とする。岩ブロックの自動消滅はスコア対象外(4.9)だが、攻撃力には数える
- 妨害ルールが無効の間は一切数えない。通常の1人プレイは無効のままで、動作・スコアとも従来と変わらない

#### 相殺

- 自分が溜めた未送信の攻撃力と、相手から届いた攻撃力を突き合わせ、**差分だけが自分の盤面に届く**
- 相殺に使った分は自分の未送信攻撃力から減らす。相手の攻撃力が自分の溜め分以下なら、こちらの盤面には何も降らない
- 相殺後に残った量は受信待ちプールへ加算する。プールは岩へ変換されるまで持ち越す

#### 岩への変換と投下

- 受信待ちプールが`attack_blocks_per_rock`に達するごとに岩1個へ変換する。1回(1ウェーブ)で降らせる個数は`attack_rocks_per_wave_max`で頭打ちにする
- 変換しきれない端数・上限を超えた分はプールに残し、次のウェーブへ繰り越す。前のウェーブの予告が残っている間は次のウェーブを始めない
- 出現行は画面上端(プレイヤーより`PLAYER_SCREEN_ROWS_ABOVE`行浅い行)とし、画面内に直接湧くのではなく上から降ってくるように見せる
- 出現列はその行のEmptyのうち、プレイヤーと設置済みボムが居ないマスからランダムに選ぶ(同じ列を二重に選ばない)。空きが無ければそのフレームでは降らせず、プールに残したまま次のフレームで再試行する
- 抽選にはボム出現位置と同じ`Game`の乱数ストリームを使う。12.6の決定性の観点では、投下のたびにこのストリームを消費する点に注意する(両者が同じtickで同じ回数だけ消費する必要がある)
- 予告時間(`INCOMING_ROCK_WARNING_MS`)が明けた時点で`Cell::Rock { hits: 0 }`として盤面へ書き込む。書き込んだ後の落下・揺れ・連結消滅は既存の重力処理(4章)にそのまま委ね、専用の落下処理は持たせない
- 予告中に出現予定マスが塞がった場合は岩を捨てず、攻撃力としてプールへ戻して次のウェーブで別の列を抽選し直す

#### 演出

- 予告は控えめにする。落下経路のEmptyマスの背景をわずかに変え、出現予定マスは残り時間に応じてフィールド背景色から岩の地色へ近づけるだけにとどめる
- 点滅・赤色・警告音は使わない。ボムの画面外警告(15.3)のような列全体の赤点滅も出さない
- 音は出現時のみ、既存の岩ヒット音を1ウェーブにつき1回鳴らす(個数は問わない)。予告開始時は無音

#### 状態と巻き戻し

- 一時停止中・ゲームオーバー中は攻撃を受け取らず、予告の残り時間も進めない。「天に召される」演出中も予告は止める
- 未送信の攻撃力・受信待ちプール・予告中の岩は状態としてスナップショットごと巻き戻す(16.5)。`attack_blocks_per_rock`と`attack_rocks_per_wave_max`は設定値なので巻き戻さない

#### 設定項目

| 設定画面の項目 | 内容 |
|---|---|
| 対戦: 岩1個に必要な攻撃力 | 岩1個へ変換するのに必要な攻撃力(`attack_blocks_per_rock`)。小さいほど岩が多く降る |
| 対戦: 一度に降る岩の上限 | 1ウェーブで降らせる岩の個数上限(`attack_rocks_per_wave_max`) |

いずれも`settings.json`へ永続化し、対戦では`BattleConfig`でホストの値を一方的に採用する(12.2)。

#### デバッグショートカット

- **O**キーで「相手から攻撃力`DEBUG_INCOMING_ATTACK_POWER`を受け取った」状態を疑似的に起こす。初回押下で妨害ルールを有効化する
- 相手が居ないため、相殺後に残った自分の攻撃力は送信済みとして捨てる
- 他のデバッグショートカットと同様、実際の対戦中は無効とする(12.5)

#### 通信層を実装するときの接続点

- 送信側は溜めた未送信の攻撃力を取り出して0に戻し、その値を相手へ送る
- 受信側は受け取った値をそのまま相殺処理へ渡す。相殺・変換・投下は受信側のインスタンスの中で完結する
- どのtickで攻撃力を交換するかは12.3のlockstepに合わせて実装時に決める。両者が同じtickで同じ手順を踏まないとデシンクする

## 15. ボム仕様(TERM独自拡張)

初代ミスタードリラーには存在しない要素。移動する敵キャラは持たず、盤面上にランダムに出現するボムが一定時間後に爆発し、周囲のブロックやプレイヤーに影響を与える。`Cell`列挙体には含めず、`Game`が`bombs: Vec<Bomb>`としてブロックとは別レイヤーで管理する。

### 15.1 出現

- 判定間隔`BOMB_SPAWN_CHECK_INTERVAL_MS`(1000ms)ごとに、盤面全体のボム数が`BOMB_MAX_COUNT_ON_BOARD`(10)未満であれば出現確率を1回抽選する
- 出現確率 = (`BOMB_SPAWN_BASE_PROB`(0.05) + `BOMB_SPAWN_DEPTH_MAX_BONUS`(0.10) × 深度進行率) × (設定の出現頻度% ÷ 100)。深度が深いほど出現しやすくなる
- 出現位置はプレイヤーの可視範囲内(画面内)にある`Cell::Empty`のマスからランダムに選ぶ。既に他のボムが占めているマス、プレイヤーが現在いるマスは候補から除外する
- 選ばれたマスと同じ行の、画面の左端か右端どちらかを出現元(`origin`)とする

### 15.2 演出段階

ボムは`Entering`→`Rolling`→`Settling`→`Ticking`の順に段階を進む。

1. **Entering**(`BOMB_ENTER_MS`=400ms): 画面端に登場してから投げるまでの間
2. **Rolling**(`BOMB_ROLL_MS`=400ms): `origin`から出現マスまで転がる間
3. **Settling**(最大`BOMB_SETTLE_MS`=600ms、`BOMB_SETTLE_TICK_MS`=80msごとに1マス移動): 支えを失っていれば重力に従って落下しつつ、左右に跳ねながら落ち着き先を探す
4. **Ticking**: 静止して起爆までカウントダウンする。`remaining_ms`はこの段階でのみ減る。Ticking中に支えを失った場合は落下を続け、落下している間は`remaining_ms`が減らない

Entering/Rollingの間は盤面のマスに何の予約も残さないため、出現時点では空いていた着地予定マスへ、演出中に別のブロックが落下してきたりプレイヤーが歩いてきたりすると重なる可能性がある。これを避けるため、Entering/Rollingの各フレームで着地予定マスが塞がっていないか再検証し、塞がれていれば同じ列の上方向にある最初の空きマスへ着地先をずらす(列の最上段まで塞がっていれば何もしない)。

### 15.3 起爆と警告演出

- 起爆までの時間は`BOMB_FUSE_MS`(5000ms、設定画面から変更可能な既定値。15.6参照)。設定変更は次に出現するボムから反映され、既に設置済みのボムの残り時間(`remaining_ms`)は変わらない
- `BOMB_DANGER_MS`(1000ms)は固定値で変更できない。起爆までの時間の設定下限は、危険域の閾値より必ず大きくなるよう`BOMB_DANGER_MS`より大きい値に固定してある
- 残り`BOMB_DANGER_MS`(1000ms)以下になると本体が激しく赤く点滅し、危険域に入った瞬間に駆け上がる警告音を1回、以降は`BOMB_FUSE_TICK_INTERVAL_MS`(200ms)間隔で導火線の連続音を鳴らし続ける
- 画面外にあるボムがいる列には、警告用の赤いライン点滅を表示する

### 15.4 爆発

- 爆風は上下に`BOMB_BLAST_ROW_RANGE`(14、画面内可視行数と同じ)、左右に`BOMB_BLAST_COL_RANGE`(フィールド最大幅と同じ)届く。岩ブロック・ダイヤブロックにも遮蔽されず、盤面の端でのみ止まる(実質「画面内の縦横全域」)
- 爆風が通過した全マスに炎の演出(`BOMB_EXPLOSION_FLASH_MS`=350ms)を表示する。中心からの距離に応じて色調を変える
- セルの中身ごとの効果:
  - 岩ブロック・ダイヤブロック → スターブロックに変わる(壊れて消えるのではない)
  - 色ブロック → その爆発ごとにランダムに選んだ1色へ塗り替える。塗り替えた結果4個以上連結したグループは、着地時の自動消滅と同じ判定でその場で消滅する
  - アイテムブロック(C/R/K) → 効果を発動させず、得点も発生させずにそのまま破壊する(取得と破壊は別物として扱う)
  - 酸素カプセル・Empty → 影響を受けない
- 爆風がプレイヤーに触れていたら、押し潰しと同じミス処理を行う
- 爆風が他のボムに届いた場合、そのボムも残り時間に関わらずその場で連鎖爆発する(誘爆)。1回の誘爆連鎖でプレイヤーが複数回巻き込まれても、ミス処理は1回のみ行う
- プレイヤーが死亡(押し潰し/酸素切れ)した場合、画面内外を問わず盤面上の全てのボムを即座に爆発させる(誘爆込み)

### 15.5 プレイヤーとの相互作用

- Settling/Ticking段階のボムは、岩ブロックと同様にプレイヤーの移動を塞ぐ障害物として扱う(Entering/Rollingの間は演出中で実体を持たず、素通りできる)
- 進行方向にボムがある状態で移動しようとすると、その先の1マスへボムを押し出す(押し出したボムはSettlingへ遷移し、以後は通常の重力・跳ねる挙動に従う)。押し出し先が盤面外・ブロック・別のボムで塞がっている場合は押し出さず、岩ブロックと同じ「1回目はぶつかって停止、同方向2回目で1段登る」段差登り判定を行う
- 進行方向のボムを掘削すると、爆発を誘発せずにその場で除去できる

### 15.6 設定

- ボムの出現頻度は設定画面から`BOMB_SPAWN_RATE_PERCENT_MIN`(0%)〜`BOMB_SPAWN_RATE_PERCENT_MAX`(2000%)の範囲で`BOMB_SPAWN_RATE_PERCENT_STEP`(100%)刻みに調整できる。既定値は他の出現率設定と同じ100%
- 2000%は判定確率が全深度で1.0に飽和する境界値(`1.0 / BOMB_SPAWN_BASE_PROB`)であり、これを超えて増やしても`BOMB_MAX_COUNT_ON_BOARD`(10、設定では変更不可の固定値)が同時存在数を制限する
- ボム爆発までの時間(表示ラベル「ボム爆発までの時間」)は設定画面から`BOMB_FUSE_MS_MIN`(2000ms)〜`BOMB_FUSE_MS_MAX`(10000ms)の範囲で`BOMB_FUSE_MS_STEP`(500ms)刻みに調整できる。既定値は`BOMB_FUSE_MS`(5000ms)。`settings.json`では`bomb_fuse_ms`キーで永続化する。デバッグショートカットは持たない(設定画面のみ)

## 16. フレーム巻き戻し仕様(TERM独自拡張)

初代ミスタードリラーには存在しない、人間プレイ向けの救済機能(#233)。プレイ中に`Backspace`または`U`を押すと数秒前の状態まで遡って再開できる。押し潰された直後に押して、潰される前からやり直す、という使い方を主眼に置く。

### 16.1 方式

`Game`構造体を丸ごとクローンしてリングバッファ(`rewind::RewindHistory`)に保持する。入力を再生し直す方式は採らない。

- 盤面・プレイヤー・ボム・全タイマー・演出フラグ・乱数(`Game.rng`)まで含めて状態ごと差し替えるため、巻き戻し後の挙動が「そもそも巻き戻さなかった場合」と完全に一致する
- `Game`の唯一クローンできないフィールドは`debug_log`(SQLite接続)で、これは`Option<Rc<DebugLog>>`として共有する。ログの記録先は巻き戻しの対象ではない
- 履歴は`Game`の外(main.rsのローカル状態)に置く。`Game`自身は「今」だけを表し、起動可否(`can_start_rewind`)・記録可否(`is_rewind_capturable`)・復元(`restore_for_rewind`)だけを提供する

### 16.2 スナップショットの記録

- 記録間隔は**実時間ではなくゲームフレーム数**で数える(`REWIND_SNAPSHOT_INTERVAL_FRAMES` = 100フレーム)。`FRAME_INTERVAL_MS`(33ms)換算で約3.3秒に1回。負荷でフレーム間隔が伸びても記録の粒度がぶれないようにするため
- 保持数の上限は`REWIND_MAX_SNAPSHOTS`(10個、≈33秒分)。超えたら最古から捨てる
- 記録するのは`status == Playing`かつ昇天演出中(`is_dying`)でないときだけ。記録しない間はフレーム数も数えない
  - 昇天演出中を除外することで、履歴の最新が常に「まだ生きていた最後の瞬間」になる
  - ここでいう昇天演出中には、最後のライフでミスして演出の完了でゲームオーバーになるケースも含む。その間はまだ`status == Playing`なので、ゲームオーバーになる前に巻き戻せる

| 状態 | 巻き戻しの起動 | スナップショットの記録 |
|---|---|---|
| `Playing`(通常) | 可 | する |
| `Playing`かつ昇天演出中(`is_dying`) | 可(主要な使い方) | **しない** |
| `Playing`かつスライダー演出中 | 可 | する |
| `Paused` | 不可 | しない |
| `GameOver` | 可(ストックと履歴があれば。ダイアログにヒントを出す) | しない |
| `Cleared` | 不可 | しない |
| アトラクトデモ中 | 不可(任意キーでタイトルへ戻る既存挙動が優先) | — |

### 16.3 ストック(使用回数)

- 初期値`REWIND_STOCK_INITIAL`(3)。1回巻き戻すごとに1消費する
- 100mチェックポイント到達ごとに`REWIND_STOCK_PER_CHECKPOINT`(1)補充し、上限でクランプする
- 上限は設定画面の「巻き戻しストック上限」(`settings.rewind_stock_max`)で`REWIND_STOCK_MAX_SETTING_MIN`(0)〜`REWIND_STOCK_MAX_SETTING_MAX`(5)に調整でき、既定は`REWIND_STOCK_MAX_DEFAULT`(3)。**0にすると機能そのものがOFF**になる(ストックも0へ切り下げられ、HUDの表示も消える)
- GameOverからの「その場から復活」(`revive`)では、ライフ・酸素と同様にストックも初期値(上限でクランプ)まで回復する

### 16.4 巻き戻し中の操作

起動すると自動で逆再生が始まり、`REWIND_PLAYBACK_MS_PER_STEP`(300ms)ごとに1スナップショットずつ過去へ進む。この間ゲーム本体は凍結し、`Game::update`は呼ばれない。

| キー | 動作 |
|---|---|
| Enter / X / Z | その時点の状態で確定して再開する |
| Esc | やめる(現在の状態のまま再開する) |
| ← | 1つ過去へ(自動逆再生は止まる。最古で停止) |
| → | 1つ未来へ(自動逆再生は止まる。開始時点の「現在」で停止) |

- 最古のスナップショットに達した時点で自動逆再生は止まる。自動で確定することはない
- 起動時に「現在」もスナップショットとして積むため、→で現在まで戻ってこられる
- カーソル0(=開始時点の現在そのもの)で確定した場合は**キャンセル扱い**とし、復元もストック消費も行わない
- 確定したら、その時点より新しいスナップショットは履歴から捨てる(起こらなかった未来へ進み直せないようにする)

### 16.5 巻き戻すもの・巻き戻さないもの

`Game`を丸ごと差し替えるため、下表の「巻き戻さない」に挙げたもの以外は全て戻る。

| 対象 | 扱い |
|---|---|
| 盤面・プレイヤー(位置/向き/酸素/ライフ/スコア/取得数/経過時間)・重力/揺れ状態・ボム・攻撃力/受信待ちプール/予告中の岩(12.8)・全タイマー・演出フラグ・乱数 | **巻き戻す** |
| `frame_counter` | 巻き戻さない(デバッグログのフレーム番号を単調増加に保つ) |
| `debug_log` | 巻き戻さない(同じ`Rc`を維持する) |
| `invincible` / `misses_averted` | 巻き戻さない(デバッグ機能の状態・累計) |
| `rewind_stock` | 巻き戻さず、現在値から1消費する |
| `rewind_stock_max` | 巻き戻さない(設定値) |
| `attack_blocks_per_rock` / `attack_rocks_per_wave_max` | 巻き戻さない(設定値。12.8) |

- **サウンド**: BGMは特別扱いしない(復元で`status`が`Playing`に戻れば既存の判定で自動再開する)。SEは復元時に何も鳴らさない(`GameEvent`を発生させない)。起動時に専用SE(`play_rewind_start`)、確定時に復活音(`play_revive`)だけを鳴らす
- **デバッグログ**: 復元時に`rewind_events`テーブルへ1行(フレーム番号・消費後の残ストック)記録する。巻き戻しの前後で盤面が不連続に飛ぶため、それがバグではないと後から判別できるようにするため
- **オートプレイ(#218)**: 巻き戻し後もONのまま続行してよいが、`Autopilot`の内部状態(位置履歴・目的列)が古い盤面を前提にしたままになるため、復元直後に作り直す

### 16.6 履歴を捨てるタイミング

以下のいずれかが起きたら、その場でリングバッファを空にする。戻った先の前提が現在と食い違う状態を作らないため。

1. 一時停止中に設定オーバーレイを開いたとき(配分率・列数・速度を変えられるため)
2. 速度系デバッグキー(`[` `]` `-` `=` `,` `.`)を押したとき
3. デバッグログのON/OFFを切り替えたとき(ログを開き直す**前**に捨てる)
4. GameOverダイアログで「その場から復活」を選んだとき
5. タイトルへ戻ったとき / 新規ゲームを開始したとき

### 16.7 表示

- HUD(ステータスパネル)に`REWIND ↺ ×N`の行を出す。設定の上限が0(OFF)なら行ごと省略する
- 巻き戻し中は、見ている時点のスナップショットをそのまま描画した上にオーバーレイを重ねる(`<< 巻き戻し中  -Nステップ (約N秒前)` と操作説明)。GameOver中にも巻き戻せるため、このオーバーレイは中央ではなくゲーム画面の下端に寄せ、GameOverダイアログと重ならないようにする
- GameOverダイアログには、`can_start_rewind()`が真のときだけ「Backspace/U: 巻き戻す(残りN)」のヒント行を足す
- ヘルプ画面の操作一覧にも「Backspace/U: 巻き戻し」を載せる
