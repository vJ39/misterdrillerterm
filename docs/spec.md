# ミスタードリラーTERM 仕様書

1999年ナムコ「ミスタードリラー」(初代)のルール・雰囲気に寄せた、ターミナル(TUI)で動く縦穴掘りアクションゲームの仕様書。
実装言語はRust。描画はratatui+crossterm、サウンドはrodioを使った自作波形合成音源(実機音源は使用しない)。

キャラクター名は初代のもの(ホリ・ススム 等)をそのまま使用する方針で確定済み。

## 1. 基本ルール

- プレイヤー(ホリ・ススム)は幅12マスの縦穴を深さ1000mまで掘り進む
- 1m = 1マス。フィールドは下方向にスクロールする
- 操作は ←/→/↓ の3方向とP(一時停止)、Q(終了)のみ
- 酸素が尽きる、または落下してくるブロックに押し潰されるとミス(ゲームオーバー)
- 深度1000mへ到達するとゲームクリア

### 操作一覧

| キー | 動作 |
|---|---|
| ← | 左に隣接するブロックを掘削して破壊し、左のマスへ移動。ブロックが無ければそのまま移動 |
| → | 右に隣接するブロックを掘削して破壊し、右のマスへ移動。ブロックが無ければそのまま移動 |
| ↓ | 真下のブロックを掘削して破壊し、1マス下降。ブロックが無ければそのまま下降 |
| P | 一時停止/再開 |
| Q | ゲーム終了(確認なしで即終了。タイトルへ戻る) |

- 岩ブロックへ向けて移動キーを入力した場合、掘削できず移動もしない(その場に留まる)
- 上方向への移動キーは無い(掘った穴を登り返す操作は無い。初代準拠)

## 2. フィールドとブロック

### フィールド構造

- 幅: 12マス(列インデックス0〜11)
- 深さ: 1000マス(行インデックス0〜999、行インデックス=深度[m])
- データ構造は `Vec<[Cell; 12]>` (要素数1000)を想定。1行=1m分の横一列

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
enum Cell {
    Empty,
    Color(ColorKind),
    Rock,
    Oxygen,
    Diamond,
}

#[derive(Clone, Copy, PartialEq, Eq)]
enum ColorKind {
    Red,
    Blue,
    Green,
    Yellow,
    Purple,
}
```

### ブロック種類

| 種類 | 見た目 | 掘削可否 | 掘削時の効果 |
|---|---|---|---|
| 色ブロック(赤/青/緑/黄/紫) | 2文字幅の色付きブロック | 掘削可 | 破壊のみ(得点なし。深度到達自体がスコアの主因) |
| 岩ブロック | 灰色ブロック | 掘削不可 | 迂回が必要。破壊されず、単独/グループで落下することもない |
| 酸素カプセル | 水色の専用グリフ | 掘削可 | 酸素+50(上限100でクランプ) |
| ダイヤブロック | 白/水色の専用グリフ | 掘削可 | 得点+500(即時加算) |

- 岩ブロックは掘削不可なだけでなく、連結落下ロジックの対象にもならない(常にその場に固定される背景扱い)
- 酸素カプセル・ダイヤブロックも連結落下ロジックの対象外(固定)。対象になるのは色ブロックの3個以上連結グループのみ(詳細は4章)

### 開始地点の安全確保

- 深度0〜1m(先頭2行)はブロック生成テーブルを適用せず、全マスEmpty固定とする
- これにより開始直後に落下ブロックへ巻き込まれる事故を防ぐ

## 3. ブロック生成アルゴリズム

深度が増すほど岩ブロックの出現率が上がるよう、100mごとではなく200m刻みの帯(バンド)でテーブルを分け、行ごと・マスごとに独立抽選する。

### 深度帯別 出現確率テーブル

| 深度帯 | 岩 | 色ブロック合計(内訳:5色均等) | 酸素カプセル | ダイヤブロック |
|---|---|---|---|---|
| 0〜199m | 5% | 90%(各色18%) | 3% | 2% |
| 200〜399m | 8% | 85%(各色17%) | 4% | 3% |
| 400〜599m | 12% | 80%(各色16%) | 4% | 4% |
| 600〜799m | 16% | 75%(各色15%) | 4% | 5% |
| 800〜1000m | 20% | 70%(各色14%) | 4% | 6% |

各行の合計は必ず100%になるよう設計済み。深度が深いほど岩が増え通行の迂回コストが上がる一方、ダイヤの出現率も上がりハイリスク・ハイリターンになる構成。

### 生成手順(擬似コード)

```rust
fn band_table(depth_m: u32) -> BandTable {
    match depth_m {
        0..=199   => BandTable { rock: 0.05, color_each: 0.18, oxygen: 0.03, diamond: 0.02 },
        200..=399 => BandTable { rock: 0.08, color_each: 0.17, oxygen: 0.04, diamond: 0.03 },
        400..=599 => BandTable { rock: 0.12, color_each: 0.16, oxygen: 0.04, diamond: 0.04 },
        600..=799 => BandTable { rock: 0.16, color_each: 0.15, oxygen: 0.04, diamond: 0.05 },
        _         => BandTable { rock: 0.20, color_each: 0.14, oxygen: 0.04, diamond: 0.06 },
    }
}

fn generate_row(rng: &mut impl RngCore, depth_m: u32) -> [Cell; 12] {
    if depth_m < 2 {
        return [Cell::Empty; 12];
    }
    let t = band_table(depth_m);
    let mut row = [Cell::Empty; 12];
    for col in 0..12 {
        let r: f32 = rng.gen_range(0.0..1.0);
        row[col] = pick_cell(r, &t); // 累積分布で判定
    }
    row
}
```

- 盤面は乱数シード(u64)から1000行を起動時に全て事前生成する(通常プレイはOS乱数から生成したシード、タイムアタック/対戦は固定・共有シードを使用。詳細は11章・12章)
- 乱数生成器は `rand_chacha::ChaCha8Rng`(シード指定可能・決定的)を使用する

## 4. 連結落下ロジック

### 対象

- **色ブロックのみ**が対象。上下左右(4方向)に同色が3個以上連結している塊(グループ)だけが落下する
- 岩・酸素カプセル・ダイヤブロック・2個以下の色ブロックは対象外で、常にその場に固定される(初代の「同色3個以上が浮遊落下する」仕様に準拠)

### 判定タイミング

- 毎フレームではなく、固定間隔の論理ティック(`FALL_TICK_MS` = 150ms、13章参照)ごとに全グループを再評価する
- 1回のティックで動くのは1マス分のみ。支持を失ったグループは以後のティックでも再評価され、着地するまで毎ティック1マスずつ連鎖的に落下し続ける

### 判定アルゴリズム

1. 未確定(既に落下中でない)の色ブロックに対し、同色・4方向連結の連結成分をUnion-Find/BFSで求める
2. 成分サイズが3未満なら対象外
3. 成分が占有する列ごとに、その列内で最も深い(行番号が最大の)マスを求める
4. その「各列の最下段マス」の直下(行+1)を確認する
   - 直下マスがフィールド最深部(行999)を超える場合は着地済みとして対象外
   - 直下マスがEmptyでない(色ブロック/岩/酸素カプセル/ダイヤ/他の未着地グループ)場合は支持ありとして対象外
   - **プレイヤーの現在位置は「空洞」として扱う**(プレイヤーはグループの支持体にならない。5章の押し潰し判定と対になる仕様)
5. 全ての列の直下マスがEmpty(またはプレイヤー位置)であれば、成分全体を1マス下へ移動する(元の位置をEmptyにし、新しい位置へ同じColorKindを配置)
6. 同一ティック内で複数グループが対象になった場合、フィールド上段(浅い深度)側から順に処理する(下段のグループが先に動いて空間を作り、その結果上段グループも同ティックで連動して動く事故を避けるため)

### 実装上の注意

- 落下中のグループは、移動先を確定した瞬間に5章の押し潰し判定にかける
- 連結成分の再計算は全マス走査ではなく、直前ティックで変化のあった行の周辺のみに限定するなど、深度1000m×幅12マス(=12,000セル)規模でも軽量に保てる設計にする

## 5. 押し潰し判定

- 4章の手順5で「成分が1マス下へ移動する」と確定した際、移動後の成分占有マスの集合に**プレイヤーの現在位置が含まれるかどうか**を判定する
- 含まれていれば、その瞬間に即ミス(ゲームオーバー)。移動アニメーションの猶予やワンテンポの回避猶予は無い
- 判定順序のまとめ:
  1. 支持判定ではプレイヤー位置を「空洞」として扱う(プレイヤーがいても塊は落下できる)
  2. 落下先確定後、その落下先とプレイヤー位置が重なっていればミス確定
- この2段構えにより「プレイヤーが立っている真上のグループが、プレイヤーごと落ちてくる」という初代同様の緊張感のある挙動になる

## 6. 酸素ゲージ

| 項目 | 値 |
|---|---|
| 最大値 | 100 |
| 自然減少速度 | 1秒あたり2.0(フレーム経過時間に応じて連続的に減少させる。`oxygen -= 2.0 * delta_seconds`) |
| 酸素カプセル取得時 | +50(上限100でクランプ。既に100の場合は超過分切り捨て) |
| 0になった場合 | 即ミス(ゲームオーバー) |

- 内部値はf32で保持し、表示は整数値に切り捨てる(端数で「残り1」のような表示になるのを避けるため)
- 酸素が20以下になったら警告音を鳴らす(10章参照)

## 7. チェックポイントとスコア

### チェックポイント

- 深度200m/400m/600m/800m/1000mの各到達時に以下を行う
  1. 酸素を100へ全回復
  2. 経過タイムに応じたタイムボーナスを加算(1000m到達時はゲームクリアを兼ねる)

### タイムボーナス計算

各チェックポイントに基準タイム(目標到達秒数)と固定の基礎ボーナスを設定する。

| チェックポイント | 基準タイム | 基礎ボーナス |
|---|---|---|
| 200m | 40秒 | 1,000点 |
| 400m | 90秒 | 1,000点 |
| 600m | 150秒 | 1,000点 |
| 800m | 220秒 | 1,000点 |
| 1000m(クリア) | 300秒 | 2,000点 |

```
タイムボーナス = 基礎ボーナス + max(0, 基準タイム - 到達時点の経過秒数) × 10
```

基準タイムより早く到達するほど加点が増え、遅れても基礎ボーナス分は保証される。数値は初期チューニング値であり、実プレイ後に調整する前提の定数として`13章`にまとめる。

### スコア合計

```
スコア = 最大到達深度(m) × 10 + 取得ダイヤ数 × 500 + Σ(各チェックポイントのタイムボーナス)
```

- 「最大到達深度×10」はリアルタイムに更新し、ステータスパネルにも常時反映する
- ダイヤの500点は取得した瞬間に確定加算する

## 8. ゲームオーバー/クリア条件

| 条件 | 結果 |
|---|---|
| 酸素が0になる | ゲームオーバー(ミス音を再生しリザルト画面へ) |
| 落下ブロックに押し潰される | ゲームオーバー(ミス音を再生しリザルト画面へ) |
| 深度1000mへ到達 | ゲームクリア(クリアファンファーレを再生しリザルト画面へ) |

リザルト画面では最終スコア・到達深度・経過タイム・(タイムアタックモードなら自己ベスト更新有無)を表示する。

## 9. TUI仕様

### 画面レイアウト

```
+----------------------------+------------------------+
| フィールド(左)             | ステータスパネル(右)   |
|                            |                        |
|  ██░░@░██░░░░░░░░░░░░░░░░  |  深度      : 123 m     |
|  ░░██░░░░◆░██░░░░██░░░░░░  |  酸素 [████████░░] 82  |
|  ██░░░░██░░░░░░▲▲██░░░░░░  |  スコア    : 1,230     |
|  ░░░░██░░░░██░░░░░░░░██░░  |  経過タイム: 00:47     |
|  ...                       |  次CPまで  : 77 m      |
+----------------------------+------------------------+
```

- フィールド側は12列×可変行(ターミナル高さに応じて可視行数を決定)。各セルは2文字幅で描画し、色付き背景(または専用グリフ)でブロック種を表現する
- プレイヤーは常に画面内の固定行(例: 上から1/3の位置)に表示し、掘り進むにつれてフィールド側を上方向にスクロールさせる(=深度が増えるとフィールド全体が上へ流れる)
- ステータスパネルは深度・酸素ゲージ(バー表示)・スコア・経過タイム・次チェックポイントまでの残り距離を表示する

### セル表示の対応(例)

| Cell | 表示 |
|---|---|
| Empty | スペース2文字(背景色のみ) |
| Color(Red) | `██` 背景RGB (255,179,179) 系パステル赤 |
| Color(Blue) | `██` 背景RGB (179,204,255) 系パステル青 |
| Color(Green) | `██` 背景RGB (186,255,201) 系パステル緑 |
| Color(Yellow) | `██` 背景RGB (255,245,179) 系パステル黄 |
| Color(Purple) | `██` 背景RGB (224,179,255) 系パステル紫 |
| Rock | `▓▓` 背景RGB (150,150,150) グレー |
| Oxygen | `▲▲` 背景RGB (179,240,255) 水色 |
| Diamond | `◆◆` 背景RGB (255,255,255) 白 |
| プレイヤー | `@ ` 背景は現在マス背景色を維持し前景色で描画 |

- 全て`crossterm::style::Color::Rgb(r, g, b)`のトゥルーカラーで指定し、全体をパステル調で統一する
- ratatuiの`Cell`/`Line`に背景色(bg)としてこれらのRGBを設定する形で実装する

### 入力処理

- crossterm rawモードを有効化し、`event::poll`+`event::read`でノンブロッキング取得するメインループを組む(ポーリング間隔目安16〜33ms、描画フレームレート30〜60fps相当)
- `KeyCode::Left`/`Right`/`Down`/`Char('p')`/`Char('q')`(大文字小文字とも受理)をハンドリングする
- 移動入力には`INPUT_COOLDOWN_MS`(13章、目安80ms)のクールダウンを設け、ターミナルのキーリピート速度差を吸収し移動速度を一定に保つ

### レイアウト実装方針

- `ratatui::layout::Layout`で`Direction::Horizontal`、`Constraint::Length(フィールド幅)`+`Constraint::Min(20)`の2ペインに分割する
- フィールド幅 = 12列×2文字+左右のボーダー分(目安26〜28カラム)

## 10. サウンド仕様

rodioの`Source`トレイトを自前実装し、サイン波/矩形波をその場で生成してSE・BGMを鳴らす。実機音源(WAV/MP3等のサンプル素材)は使用しない。

### 波形ジェネレータの実装方針

```rust
struct SquareWave {
    freq: f32,
    sample_rate: u32,
    num_sample: usize,
    amplitude: f32,
}

impl Iterator for SquareWave {
    type Item = f32;
    fn next(&mut self) -> Option<f32> {
        self.num_sample = self.num_sample.wrapping_add(1);
        let t = self.num_sample as f32 / self.sample_rate as f32;
        let phase = (t * self.freq).fract();
        Some(if phase < 0.5 { self.amplitude } else { -self.amplitude })
    }
}

impl rodio::Source for SquareWave {
    fn current_frame_len(&self) -> Option<usize> { None }
    fn channels(&self) -> u16 { 1 }
    fn sample_rate(&self) -> u32 { self.sample_rate }
    fn total_duration(&self) -> Option<std::time::Duration> { None }
}
```

- `SineWave`も同様の構造体で`amplitude * (2.0 * PI * t * freq).sin()`により実装する
- 各SEは上記の無限長Sourceに対し`.take_duration(Duration::from_millis(N))`で長さを切り、`.amplify(音量)`で音量調整、必要に応じ簡易フェードアウト(末尾数msで振幅を線形に0へ収束)をかけてクリック音(プチノイズ)を防ぐ

### SE一覧

| SE | 発生タイミング | 波形 | 周波数/長さ |
|---|---|---|---|
| 掘削音 | 掘削入力を受け付けた瞬間(ブロックの有無に関わらず) | 矩形波 | 440Hz、20ms |
| 破壊音 | ブロックが破壊され消滅した瞬間 | 矩形波(下降チャープ) | 220Hz→110Hz、60ms |
| air取得音 | 酸素カプセル取得時 | 矩形波2音 | 523Hz(60ms)→784Hz(60ms) |
| 酸素警告音 | 酸素残量が20以下の間、1秒間隔で | 矩形波 | 880Hz、200ms |
| チェックポイント到達音 | 200/400/600/800m到達時 | 矩形波4音アルペジオ | 523/659/784/1046Hz、各80ms |
| クリアファンファーレ | 1000m到達時 | 矩形波(チェックポイント音の拡張) | 523/659/784/1046/1318Hz、各100ms |
| ミス音 | ゲームオーバー時 | 矩形波(下降チャープ) | 440Hz→110Hz、500ms |
| 掘削失敗音(任意) | 岩ブロックへ入力した時 | 矩形波(低音単発) | 110Hz、30ms |

### BGM

- 矩形波による簡易チップチューン、4小節ループ
- テンポ140BPM(1拍=約428.6ms)、1小節=8分音符8ステップの単声ベースラインを基本形とする
- 参考ノート列(実装時に耳で微調整する前提の初期値):
  - 1小節目: C4 E4 G4 E4 C4 E4 G4 E4
  - 2小節目: A3 C4 E4 C4 A3 C4 E4 C4
  - 3小節目: F3 A3 C4 A3 F3 A3 C4 A3
  - 4小節目: G3 B3 D4 B3 G3 B3 D4 B3(4小節目終端で1小節目へループ)
- 別スレッド(`std::thread::spawn`)で`OutputStream`+`Sink`を保持し、ノート列を`.append()`し続けるループ再生を行う
- 音量はBGM用Sinkで0.25前後、SE用Sinkで0.6〜0.8を目安とし、BGMがSEを埋もれさせないバランスにする(同一`OutputStream`上に複数`Sink`をぶら下げて個別音量調整する)

## 11. タイムアタックモード仕様

ノーマルコースと同一の盤面生成ロジック(2〜4章)・落下ロジック・押し潰し判定・酸素ルールをそのまま流用し、勝敗条件を「タイム」に絞ったモード。

### 目的

- 盤面のランダム性による有利不利を排除し、純粋なプレイヤースキルの比較(自己ベスト更新)を可能にする

### 固定シード

- タイムアタックモードは常に固定シード `TIME_ATTACK_SEED: u64 = 0x4D444C31_54494D45`(実装時に任意の固定値で確定させてよい。要は「毎回同じ値」であることが重要)を使用する
- これにより毎回全く同じ盤面(岩配置・色ブロック配置・酸素カプセル/ダイヤの位置)が生成され、タイム差が純粋にプレイヤーの操作速度・判断に由来するようになる

### 計測方法

- ゲーム開始(最初の入力を受け付けた瞬間、またはカウントダウン終了時)から、深度1000m到達(ゴール)またはミスによる終了までの経過時間をミリ秒単位で計測する
- ミスで終了した場合は「未完走」として記録し、自己ベストの更新対象にしない(完走タイムのみを比較対象とする)
- 経過タイムはノーマルモードと同じくステータスパネルに常時表示する(7章のチェックポイントボーナスもタイムアタックモードで有効のまま、参考スコアとして表示するが、モードの主目的はタイムそのもの)

### 自己ベスト記録の保存

- OSごとのユーザーデータディレクトリ(`dirs`クレートの`data_local_dir()`等を想定)配下に`misterdrillerterm/time_attack_best.json`として保存する
- 保存内容:

```json
{
  "seed": 5548943881099852613,
  "best_time_ms": 187342,
  "achieved_at": "2026-07-25T12:34:56+09:00",
  "attempts": 12
}
```

- `seed`は固定値だが、将来シードを変更した場合に旧記録と混同しないよう記録に含めておく(読み込み時にシード不一致ならレコードをリセットする)
- クリア(1000m到達)する度に`best_time_ms`と比較し、更新されていれば上書き保存。`attempts`は挑戦回数(クリア/ミス問わず開始した回数)をインクリメントする
- リザルト画面で「自己ベスト更新」の有無と、更新した場合は旧ベストとの差分(短縮ms)を表示する

## 12. ネットワーク対戦モード仕様

次フェーズの実装者がそのまま実装に落とせる粒度で、UDPブロードキャストによる対戦相手自動探索→TCP接続→lockstep同期の全手順を規定する。

### 全体フロー概要

```
[起動・対戦モード選択]
        |
        v
[UDP: HELLO を1秒間隔でブロードキャスト送信 + 受信待ち]
        |  (他ホストのHELLOを受信して候補リストに表示)
        v
[プレイヤーが候補を選びINVITE送信] --> [相手がACCEPT/DECLINEを返す]
        |  (ACCEPT)
        v
[UDPブロードキャスト停止]
        |
        v
[TCP接続確立(ACCEPT側がlisten、INVITE側がconnect)]
        |
        v
[TCPハンドシェイク: Hello交換 → シード決定(SeedAgree) → StartCountdown]
        |
        v
[lockstep対戦ループ: 毎tickInput交換 → 両者が確定的にシミュレーション]
        |
        v
[先に500m到達 or 切断 → Result交換 → 対戦終了]
```

### 12.1 UDPブロードキャストによる自動探索

#### ポート番号

| 用途 | プロトコル | ポート |
|---|---|---|
| 対戦相手探索(HELLO/INVITE/ACCEPT/DECLINE/BYE) | UDP | 39393 |
| ゲーム開始後の本接続(既定値。実際に使う値はHELLOパケットで相手に通知する) | TCP | 39394 |

- ブロードキャスト送信先は`255.255.255.255:39393`(サブネット限定ブロードキャストが必要な環境向けに、各ネットワークインターフェースのIPv4アドレスから求めた directed broadcast アドレスへ個別送信するフォールバックも実装しておくことが望ましい)
- ソケットは`SO_BROADCAST`を有効化し、同一ポートで送信と受信の両方を行う(`UdpSocket::bind("0.0.0.0:39393")`)

#### パケットフォーマット(固定長60バイト、リトルエンディアン)

| オフセット | サイズ | フィールド | 内容 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `"MDT1"` (0x4D 0x44 0x54 0x31)。プロトコル識別子 |
| 4 | 1 | packet_type | u8。下記「パケット種別」参照 |
| 5 | 1 | protocol_version | u8。現在は`1`固定 |
| 6 | 16 | sender_id | 送信者のプレイヤーID(UUID v4の生バイト列。起動時に1回生成しセッション中固定) |
| 22 | 16 | target_id | 宛先プレイヤーID。HELLO/BYEでは全ゼロ固定。INVITE/ACCEPT/DECLINEでは相手のsender_idを指定 |
| 38 | 16 | player_name | 表示名。UTF-8バイト列を16バイトに収め、余りは`0x00`でパディング(16バイト超は切り詰め) |
| 54 | 2 | tcp_port | u16。このホストがゲーム開始後にlistenするTCPポート(既定`39394`。使用中なら`39395`, `39396`…と1つずつ空きを探して採用する) |
| 56 | 4 | reserved | 将来拡張用。送信時は全`0x00`、受信時は無視する |

合計: 60バイト固定長。

#### パケット種別(packet_type)

| 値 | 名称 | 意味 | target_id |
|---|---|---|---|
| 0x01 | HELLO | 生存/募集アナウンス。1秒間隔で送信し続ける | 全ゼロ |
| 0x02 | INVITE | 対戦招待 | 招待相手のsender_id |
| 0x03 | ACCEPT | 招待受諾 | 招待者のsender_id |
| 0x04 | DECLINE | 招待拒否 | 招待者のsender_id |
| 0x05 | BYE | 探索/募集からの離脱通知(候補リストからの即時除去用) | 全ゼロ |

#### 候補リストの管理

- 自ホストと異なる`sender_id`のHELLOを受信するたびに、候補リスト(`sender_id -> (player_name, ip_addr, tcp_port, 最終受信時刻)`)を更新する
- 最終受信から5秒(`DISCOVERY_TIMEOUT_MS` = 5000)経過した候補は一覧から自動的に除去する
- BYEを受信した場合は即座に該当候補を除去する

#### 招待から接続確立まで

1. プレイヤーがTUI上で候補を選びEnterすると、選んだ相手の`sender_id`を`target_id`に設定したINVITEを送信し、応答待ち状態(タイムアウト`INVITE_TIMEOUT_MS` = 10000)に入る
2. 招待された側はINVITEダイアログを表示し、Y(承諾)/N(拒否)で応答する
   - Y: `target_id`=招待者の`sender_id`としたACCEPTを返す。自身は以後TCPサーバ役として、自分のHELLOで広告した`tcp_port`で`TcpListener::bind`しlistenを開始する
   - N: DECLINEを返し、探索状態を継続する
3. INVITEを送った側がACCEPTを受信したら、UDPブロードキャスト送信を停止し、ACCEPTの送信元IPアドレス＋そのホストが最後に広告していた`tcp_port`へ`TcpStream::connect`する(=INVITE側がクライアント役)
4. 3秒(`TCP_CONNECT_TIMEOUT_MS` = 3000)以内に接続確立できない場合は対戦不成立とし、双方ともUDP探索状態(HELLO再送)へ戻る

### 12.2 TCP接続確立後のゲーム開始シーケンス

TCP接続後は、4バイトのビッグエンディアン長さプレフィックス(u32、以降のペイロードのバイト数)+ペイロードでフレーミングする。ペイロードは`serde`+`bincode`でシリアライズする。

```rust
#[derive(Serialize, Deserialize)]
enum GameMessage {
    Hello { name: String },
    SeedAgree { seed: u64 },
    StartCountdown { start_at_unix_ms: u64 },
    Input { tick: u32, action: InputAction },
    Heartbeat { tick: u32 },
    Result { reached_goal: bool, time_ms: u64 },
    Bye,
}

#[derive(Serialize, Deserialize, Clone, Copy)]
enum InputAction {
    None,
    Left,
    Right,
    Down,
}
```

シーケンス:

1. 接続確立直後、両者が`Hello { name }`を送り合い、相手の表示名をTUIに反映する
2. **TCPサーバ役(ACCEPTした側)** がOS乱数から64bitのシードを生成し、`SeedAgree { seed }`をクライアント役へ送信する。クライアント役はこの`seed`をそのまま採用する(=両者は必ず同一シードを使用する。サーバ役が単独決定することで「どちらのシードを使うか」の合意プロトコルを省略している)
3. 両者は受信/生成した`seed`を使い、2〜4章の生成アルゴリズムでそれぞれのローカルに1000行のフィールドを生成する(この時点で両者のフィールドは完全一致するはずであり、以後は入力のみで状態が分岐しないようにする)
4. サーバ役が`StartCountdown { start_at_unix_ms }`(現在時刻+3000ms程度)を送信し、両者はローカルの時計でその時刻になるまで「3, 2, 1, GO」のカウントダウンをそれぞれ独立表示してから対戦を開始する(NTP的な厳密同期は行わず、この程度の簡易同期で十分とする)
5. 対戦開始後は12.3のlockstepループに入る

### 12.3 lockstep方式での盤面同期

#### 基本方針

- 対戦は固定の論理tick(`FALL_TICK_MS` = 150ms。通常プレイの落下判定tickと同じ値を流用する)で進行する
- 各tickで両者はその瞬間の入力(何もしていなければ`InputAction::None`)を1つ確定し、`Input { tick, action }`として相手に送信する
- 自分のtick分の入力を確定させると同時に、相手から届いた同じtick番号の`Input`を待つ。**両者の当該tickの入力が揃って初めて、そのtickのシミュレーション(移動・掘削・4章の落下判定・6章の酸素減少)を実行する**。これがlockstepの核であり、乱数は起動時のフィールド生成にしか使わないため、同一シード+同一入力列から両者は必ず同一の状態遷移をたどる
- 相手の入力が届かない場合は最大500ms(`LOCKSTEP_WAIT_TIMEOUT_MS`)待機する。タイムアウトした場合は相手の切断とみなし対戦を中断する(相手の不戦敗扱い)

#### ネットワーク遅延対策(将来拡張)

- 初期実装では上記の「揃うまで待つ」素朴な同期で問題ない(対戦専用LANが前提のため遅延は小さい)
- 体感遅延が問題になる場合は、入力を1〜2tick先行してバッファする「入力遅延バッファ方式」への拡張を想定しておく(本仕様のtick番号付きInputメッセージはそのまま流用できる設計にしてある)

#### 通常プレイとの操作感の違い(明記しておく仕様上の注意点)

- 通常(1人プレイ)モードの移動は押下即座に反映されるのに対し、対戦モードは入力が150ms周期のtickに量子化される。これは決定論的シミュレーションを成立させるための意図的な仕様差であり、実装漏れ・バグではない

### 12.4 対戦ルールと決着判定

- 両者は同一シードで生成された同一盤面を、同時にスタートしてそれぞれ独立に掘り進む
- **深度500mへ先に到達した方の勝ち**とする
- 到達判定は自分のローカルシミュレーションで確定するため、500m到達tickの`tick`番号と`time_ms`(StartCountdownの`start_at_unix_ms`からの経過時間)を`Result { reached_goal: true, time_ms }`として相手に通知する
- 相手から受け取った`Result`と自分の状態を突き合わせ、tick番号が早い方を勝者と判定する。同一tickで両者が同時に500m到達した場合は引き分けとする
- どちらかがミス(酸素0/押し潰され)で脱落した場合、`Result { reached_goal: false, time_ms }`を送り、生存側の勝ちとする。両者が同一tickで同時にミスした場合は引き分けとする
- 対戦中にTCP接続が切断された場合、切断を検知した側の不戦勝とする(検知はソケットエラーまたはHeartbeatの`HEARTBEAT_TIMEOUT_MS`(目安2000ms)超過で行う)

### 12.5 実装メモ

- ネットワーク送受信は専用スレッド(`std::thread::spawn`)を立て、`std::sync::mpsc`チャネルでメインのゲームループ(TUI描画・入力処理)と受け渡す設計とし、既存のratatui同期描画ループをブロックしないようにする
- `uuid`クレートで`sender_id`/`target_id`用のUUID v4を生成する
- パケットの`player_name`フィールドはUTF-8のマルチバイト文字境界で切り詰めないよう、切り詰め処理はchar境界を考慮して実装する
